    Final Project Methodology

    Final project schedule

    Section titled “Final project schedule”
    Part Date Submission or examination
    1. Ray implementation December 1, 2026, 11:59:59 pm UTC−04:00 Submit a working implementation of your solution using Ray.
    2. Architecture report January 1, 2027, 11:59:59 pm UTC−04:00 Submit a report explaining the architecture without Ray and each of its components in depth.
    3. Final examination Dates follow the official exam timetable First week (first attempt): oral defense of the project implemented without Ray. Second week (second attempt, revalorization): oral defense under the same requirements. Third attempt: handwritten examination.

    Level-two fault tolerance. For both oral defenses, the system must maintain client-side functionality and recover when any two components fail simultaneously. This includes two logical processes, two entire nodes, or a process and a separate node. Losing a node takes down every process it hosts.

    Architecture report template

    Section titled “Architecture report template”
    1. Service and guarantees. Identify the clients, the operations they need, and the observable results your system promises.
    2. Architecture without Ray. Diagram the nodes, the processes on each node, and their communication paths. For each responsibility Ray handled, explain which component takes it over and how.
    3. Component profile. Repeat for every component: responsibility, placement, inputs and outputs, state owned (if any), dependencies, and protocol. Explain how it makes decisions, why you chose that design, and how it handles its own failure or a dependency’s failure.
    4. End-to-end operation. Trace one request specific to your project from the client to the result. Identify the messages, decisions, and state changes at each step.
    5. Two failures and recovery. Explain why your design covers every pair of components. You may group pairs that behave alike if you justify the grouping. For one representative pair, trace the same request through failure and recovery. Describe what the client observes and how you would verify that the promised functionality is maintained.

    One assessment contract, twenty problem domains

    Section titled “One assessment contract, twenty problem domains”

    The twenty project topics are intentionally different. A media-streaming service, authoritative DNS service, peer-to-peer application, calendar, crawler, object store, or vector-search system should not look architecturally identical.

    They are nevertheless evaluated through the same distributed-systems contract:

    Given a problem, identify the guarantees that matter, build a distributed solution, expose the mechanisms hidden by middleware, challenge the solution under controlled faults/workloads, and defend what it actually guarantees.

    You are not rewarded for choosing an intrinsically easier application domain or punished for choosing one with more visible application features. The important work is the distributed design, implementation, experimentation, analysis, and individual defense.

    Every project starts from a problem description, not a required algorithm.

    Raft, Paxos, primary/backup replication, quorum approaches, DHTs, gossip, CRDTs, consistent hashing, 2PC, sagas, leaderless designs, caches, queues, and related techniques are available design choices when their guarantees fit the problem. A course keyword is never a sufficient architectural justification by itself.

    The three-phase progression

    Section titled “The three-phase progression”
    Phase 1
problem → Ray prototype → behavioral contract → middleware dependency map

                    ↓ Ray removal boundary

Phase 2
same problem → native architecture → explicit distributed mechanisms

                    ↓

Phase 3
fault/workload campaign → evidence → Ray/native comparison → individual defense

    The important invariant across all three phases is the application problem and externally visible behavioral contract. The internal architecture is expected to change.

    Phase 1 — Distributed prototype with Ray (15%)

    Section titled “Phase 1 — Distributed prototype with Ray (15%)”

    Purpose

    Section titled “Purpose”

    Ray Core is used as a temporary middleware scaffold so you can understand the application problem before spending most of your effort constructing infrastructure.

    Tasks, actors, object references, resource scheduling, concurrency, and runtime failure behavior may make the first version much shorter than the later native implementation. That difference is intentional.

    The question is not only:

    Can Ray solve this?

    It is also:

    What did Ray have to do for this apparently simple application code to work across processes or machines?

    Required Phase 1 artifacts

    Section titled “Required Phase 1 artifacts”

    1. Working Ray prototype

    Section titled “1. Working Ray prototype”

    The prototype must implement the minimum functional contract for the selected topic and demonstrate genuine distributed execution over multiple workers/processes where the domain allows it.

    2. Architecture diagram

    Section titled “2. Architecture diagram”

    The diagram must show your logical application components and the important Ray/runtime components on which those components depend.

    3. Behavioral/API contract

    Section titled “3. Behavioral/API contract”

    Define the externally visible operations and important outcomes without encoding Ray-specific internals into the contract.

    For example, clients should depend on concepts such as:

    submit job
query job
store object
read object
send message
search documents

    rather than concepts such as:

    call actor named X
read ObjectRef Y

    unless those concepts are genuinely part of the problem domain.

    4. Middleware dependency map

    Section titled “4. Middleware dependency map”

    For every important distributed requirement, identify what currently provides it.

    A typical map may look like:

    Requirement Phase 1 mechanism Question for the native redesign
    remote execution Ray task What explicit worker protocol is needed?
    stateful worker Ray actor Which process owns the state and how is it recovered?
    scheduling Ray runtime Does this application need dynamic scheduling at all?
    remote result ObjectRef Is a job ID + result store sufficient?
    membership Ray runtime Registry, static bootstrap, gossip, DHT, coordinator?
    retry Ray/runtime policy What are the operation’s real retry semantics?
    resource assignment Ray logical resources Which resource constraints matter to this domain?
    monitoring Ray/runtime observability What evidence must the native design expose?

    5. Initial experiment

    Section titled “5. Initial experiment”

    Phase 1 must include at least one controlled failure, concurrency, or workload experiment. The purpose is to reveal runtime behavior before you remove the runtime.

    Useful examples include worker crash, slow task, concurrent submissions, lost/failed work, or saturation.

    Phase 1 exit gate

    Section titled “Phase 1 exit gate”

    Before crossing the Ray boundary, you must be able to answer:

    • What problem does my application solve?
    • What externally visible behavior must survive the redesign?
    • Which behavior currently comes from my code?
    • Which behavior currently comes from Ray?
    • Which failure semantics did I observe rather than assume?

    The behavioral contract is then frozen unless a later change is explicitly justified.

    Ray removal boundary

    Section titled “Ray removal boundary”

    After Phase 1, Ray is prohibited as a runtime dependency for the final-project implementation.

    Ray may still be cited in the report or used as an architectural comparison. It may not silently return through another component that delegates the core distributed behavior back to Ray.

    The goal is not to reproduce all of Ray.

    Ask:

    Which distributed capabilities does this particular application actually need?

    A specialized native solution will normally implement far fewer capabilities than a general-purpose distributed runtime. That is a feature of the exercise, not a deficiency.

    Phase 2 — Native distributed-system design (50%)

    Section titled “Phase 2 — Native distributed-system design (50%)”

    Purpose

    Section titled “Purpose”

    Rebuild the same externally visible problem using explicit distributed mechanisms whose behavior you can inspect, test, and explain.

    The core implementation should normally use Go for native services. Another language may be justified when the project domain has a strong reason, but changing language cannot be used to hide the required distributed mechanisms behind another framework.

    Required architectural decisions

    Section titled “Required architectural decisions”

    The design must make the following questions explicit where applicable:

    • Communication: What protocol/API connects processes?
    • Identity: How are clients, nodes, objects, jobs, or operations identified?
    • Discovery/bootstrap: How does a process initially find the system?
    • Membership: How does the system represent current participants?
    • State ownership: Which node is authoritative for each piece of state?
    • Durability: When can an operation truthfully be acknowledged as durable?
    • Replication: Which state is copied, where, and why?
    • Consistency: Which histories may clients observe?
    • Retries: Which operations are safe to repeat, and how are duplicates detected?
    • Failure detection: How is suspicion produced and how does it affect behavior?
    • Partition policy: Which side, if any, may continue authoritative work?
    • Recovery: What happens when a failed/rejoining node returns?
    • Reconciliation: How are divergent replicas/logs/metadata repaired?
    • Scheduling: Who decides where work runs when scheduling exists?
    • Backpressure: What prevents overload from becoming unbounded work?
    • Observability: Which evidence reveals state transitions and failures?
    • Security: Who is trusted to do what, and how is that decision enforced?

    Not every project needs an elaborate answer to every item. Every project must explain why an omitted mechanism is unnecessary.

    Architecture decision record

    Section titled “Architecture decision record”

    Phase 2 should include a compact decision table such as:

    Requirement Ray Phase 1 Native candidates Selected design Reason / trade-off
    discovery runtime static / registry / gossip / DHT … …
    state actor local disk / primary / replicated log / CRDT … …
    retry runtime policy idempotency / dedup / no retry … …
    failover runtime restart / election / reroute … …

    The table is evidence that you removed abstractions intentionally rather than replacing Ray by a random collection of technologies.

    External infrastructure and libraries

    Section titled “External infrastructure and libraries”

    In the implementation without Ray, your own code must manage every distributed operation, including those outside the project’s main focus. Any library, framework, service, or infrastructure feature that simplifies or hides a distributed operation your code does not manage is forbidden. For example, you may use a library to serialize a message, but if a service automatically selects a replica and redirects clients after a failure, it has taken over failover.

    If you are unsure about a dependency or feature, ask the instructors before using it. Describe the operation and explain which decisions your code makes. If you receive no reply, the answer is no.

    Phase 3 — Verification, comparison, and defense (35%)

    Section titled “Phase 3 — Verification, comparison, and defense (35%)”

    Purpose

    Section titled “Purpose”

    Phase 3 changes the question from:

    Does the normal case work?

    to:

    What does this system guarantee under the failures and workloads that matter to this problem, and what evidence supports that statement?

    The system is not primarily extended with more application features during this phase. You establish the behavior of the design you already built.

    Shared scenario vocabulary

    Section titled “Shared scenario vocabulary”

    The course maintains a canonical Fault and Workload Scenario Library. Scenario names remain stable across module laboratories and final projects so experiments are comparable.

    Important examples include:

    • F0 Baseline — establish the normal reference execution;
    • F1 Single process crash and F2 Crash and restart;
    • F3 Slow node and F4 Packet loss;
    • F5 Minority partition or F6 Symmetric application partition;
    • F7 Heal and reconcile;
    • F8 Lost response after successful effect;
    • F9 Duplicate request delivery;
    • F10 Stale discovery;
    • F11 Stale replica read and F12 Concurrent conflicting writes;
    • F13/F14 2PC coordinator/participant failure where transactions apply;
    • F15 Leader failure where leader-based coordination applies;
    • F16 Overload and F17 Retry amplification;
    • F18 Churn for decentralized membership/placement systems;
    • F19 Disconnected CRDT updates;
    • F20 Unauthorized operation and F21 Replay of authenticated mutation.

    Reusable workloads include sequential sanity, concurrent independent operations, hot-key/hot-shard contention, read-heavy/write-heavy mixes, cross-shard operations, fan-out queries, and long-running jobs.

    Common minimum campaign

    Section titled “Common minimum campaign”

    Every final project should normally include scenarios equivalent to:

    1. baseline normal behavior;
    2. one service-node crash;
    3. crash/restart and recovery;
    4. delay or packet-loss degradation;
    5. a network partition and subsequent heal/reconciliation;
    6. duplicate request or lost-response retry semantics;
    7. concurrent workload;
    8. sustained overload when the domain exposes capacity limits.

    The exact scenario IDs depend on the architecture. A project should not invent architectural elements merely to satisfy a predefined scenario. Failure tests must follow from the design you actually chose and from the guarantees you claim.

    Project-specific campaign

    Section titled “Project-specific campaign”

    Each project then adds scenarios that challenge its distinctive guarantees.

    Examples:

    • event log: partition leadership, consumer restart, duplicate processing;
    • collaborative editor: F19 disconnected concurrent edits and merge-order variation;
    • distributed calendar: conflicting concurrent meeting updates and offline synchronization;
    • crawler: worker crash after fetch-before-acknowledgement and overload/backpressure;
    • object store: acknowledged write followed by storage-node loss and repair;
    • media streaming: storage-source failure during active playback;
    • DHT/P2P project: F18 churn and lookup/transfer success;
    • authoritative DNS: node loss, stale or divergent zone state, update visibility, partition behavior, and recovery/readiness;
    • vector search: unavailable shard and partial-result policy;
    • agent platform: tool/agent failure, duplicate action request, F20/F21 authorization/replay checks.

    Experiment record

    Section titled “Experiment record”

    Each significant experiment should include:

    scenario
workload
claim under test
prediction
configuration
fault trigger
collected evidence
observed result
conclusion
remaining uncertainty

    Screenshots may support an experiment but should not be the only evidence when structured logs, traces, metrics, persistent state, or machine-readable histories are available.

    Ray/native comparison

    Section titled “Ray/native comparison”

    Compare the Phase 1 prototype and Phase 2 native implementation using dimensions relevant to the problem. Possible dimensions include:

    • implementation complexity;
    • number of explicit mechanisms;
    • dependencies;
    • startup behavior;
    • throughput;
    • p50/p95/p99 latency;
    • recovery time;
    • failure behavior;
    • resource use;
    • operational/debugging complexity;
    • guarantees present in one implementation but absent in the other.

    There is no requirement that the native solution outperform Ray.

    A strong conclusion might instead show that the native implementation is smaller and more understandable because it deliberately omits general-purpose scheduling, object management, autoscaling, or other capabilities the application does not need.

    Individual technical defense

    Section titled “Individual technical defense”

    You must personally be able to operate and reason about the submitted system.

    The defense may ask you to:

    • predict a new fault before it is injected;
    • locate where a guarantee is implemented;
    • identify an invariant;
    • interpret a distributed trace/history;
    • explain why an operation is or is not idempotent;
    • state the consistency model in terms of observable histories;
    • identify a single point of failure;
    • explain a timeout or lease choice;
    • modify a small part of the implementation;
    • compare an alternative architecture;
    • explain an AI-generated suggestion you accepted or rejected.

    Passing public tests does not replace this individual competence requirement.

    Common distributed-systems baseline

    Section titled “Common distributed-systems baseline”

    All native projects must define and test the following where the domain makes them meaningful:

    • multiple independent service processes/nodes;
    • no implicit shared memory between logical nodes;
    • explicit network communication;
    • concurrent clients, jobs, users, or operations;
    • discovery/bootstrap/membership;
    • durable acknowledged state;
    • single-node failure behavior;
    • latency/loss/partition behavior;
    • recovery and reconciliation;
    • retry and duplicate-operation semantics;
    • configurable deployment parameters;
    • structured logs and stable identifiers sufficient for diagnosis;
    • an explicit trust/security model;
    • fully local and reproducible mandatory execution;
    • transparent public deterministic tests.

    A partition does not imply that both sides must remain writable. You must state the consistency/availability trade-off selected by the architecture.

    Silent state corruption, undefined recovery, or an implementation that claims success without satisfying its declared durability semantics is not acceptable.

    Section titled “Phase 2 — 50%”
    Criterion Weight
    Architecture and justification 10%

    Distributed correctness 10%

    Phase 3 — 35%

    Section titled “Phase 3 — 35%”
    Criterion Weight
    Fault/workload campaign 10%
    Correctness/guarantee analysis 5%
    Ray/native comparison 5%

    Optional application features may improve a strong project, but they cannot compensate for missing mandatory distributed-system behavior.

    AI-assisted engineering and disclosure

    Section titled “AI-assisted engineering and disclosure”

    AI assistants and coding agents are permitted unless an activity explicitly declares an AI-independent checkpoint.

    The governing principle is:

    You may delegate work to AI, but you may not delegate responsibility for correctness.

    Each assessed repository includes a lightweight disclosure such as:

    ai_use:
  used: true
  tools:
    - ChatGPT
    - Codex
  activities:
    - architecture discussion
    - implementation
    - debugging
    - test generation
  verification:
    - public tests
    - fault/workload campaign
    - race detector
    - manual review

    Full prompt transcripts are not normally required.

    AI output should be treated as a hypothesis, patch, design proposal, or debugging suggestion. You must determine whether it is correct through review, tests, controlled experiments, and reasoning.

    During the defense, inability to explain or modify AI-assisted work can affect the grade even when the submitted program passes its tests.

    Public testing contract

    Section titled “Public testing contract”

    There are no hidden correctness tests designed to prevent local verification.

    Official deterministic cases are readable and runnable locally. You may run them without limits and are encouraged to add your own tests.

    Optional CI/CD runs the same public checks in a repository you control. Experimental scenarios are also disclosed; evaluation may choose a disclosed scenario with different safe parameter values or workload data, but should not depend on a secret category of failure you had no opportunity to investigate.

    Third-party references and trademarks

    Section titled “Third-party references and trademarks”

    Historical and contemporary systems are cited throughout the project catalog to help you understand architectural lineage and close functional comparisons. These references do not turn an assignment into a clone of the named system.

    Your project must use independent names and branding. Third-party product names, project names, logos, service marks, trade dress, and distinctive visual identities remain the property of their respective owners.

    References are descriptive and educational and do not imply affiliation, sponsorship, endorsement, certification, or official compatibility.

    Where a project description names systems such as Ray, Apache Kafka, Apache ZooKeeper, Kubernetes, etcd, GitHub Actions, WhatsApp, Spotify, Amazon S3, Google Calendar, Cloudflare, or other third-party products/projects, preserve that distinction in reports, interfaces, repositories, and presentations.
