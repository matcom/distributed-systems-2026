    Coordination II — Mutual Exclusion, Elections, and Agreement

    Reference view. This page is optional context; return to the Lesson for the required path.

    Chapter 7 combines the previous chapters into one authority protocol: uncertain failure detection triggers elections, majority intersection preserves information, replicated logs establish order, and persistent metadata survives process restarts.

    Failure-model connection

    Section titled “Failure-model connection”

    Election timeout is built on Chapter 10 suspicion. A follower does not need perfect proof that the leader died before starting a new election.

    Safety instead relies on:

    • increasing terms;
    • durable voting state;
    • majority intersection;
    • log freshness;
    • commit rules.

    This is a central distributed-systems pattern: imperfect failure detection can coexist with strong safety.

    Time connection

    Section titled “Time connection”

    Terms are logical epochs, not physical time. Election timeout uses local elapsed duration for liveness.

    Do not use Lamport-clock magnitude to implement seconds, and do not use wall-clock timestamps as leader authority.

    Replication connection

    Section titled “Replication connection”

    Chapter 9 showed that static primary/backup leaves leader replacement underspecified. Consensus adds a protocol for choosing a leader whose log is safe and for establishing one committed operation order.

    Quorum/majority intersection now protects not only read/write overlap but future decision preservation.

    RPC connection

    Section titled “RPC connection”

    Raft itself is implemented through remote messages subject to loss, duplication, delay, and retry.

    RequestVote and AppendEntries handlers therefore need idempotent/state-machine-like transition rules. A repeated message must not create a second logical vote or corrupt the log.

    Client requests remain ambiguous if the response is lost after commitment; Chapter 10 carries request IDs into durable state-machine recovery.

    Operating Systems / storage connection

    Section titled “Operating Systems / storage connection”

    currentTerm, votedFor, and log state must survive the crash-recovery assumptions used by the safety proof.

    The order:

    persist safety-relevant state
then send response that relies on it

    can be critical.

    Computer Networks connection

    Section titled “Computer Networks connection”

    Partitions decide which groups can form a majority. Delay and loss may reduce liveness, create elections, or slow replication, but must not allow conflicting committed log entries.

    Network topology also affects practical quorum latency, although the base algorithm reasons primarily about communicating node sets.

    State-machine connection

    Section titled “State-machine connection”

    Consensus ends at an agreed committed log prefix. Chapter 10 begins the recovery problem from there.

    consensus -> committed commands -> deterministic state machine -> client-visible service

    Keeping these layers separate makes implementation and debugging easier.

    Transactions / sharding connection

    Section titled “Transactions / sharding connection”

    One consensus group can strongly order one replicated shard or metadata service. Chapter 11 asks what happens when one logical transaction spans several independently ordered groups.

    Consensus within each shard does not automatically make the cross-shard transaction atomic.

    Authoritative-DNS connection

    Section titled “Authoritative-DNS connection”

    P18 can use consensus or another strongly ordered replication strategy for the administrative zone-update path while keeping ordinary DNS query serving read-heavy and highly available. Consensus is therefore a design option for authoritative control-plane state, not a requirement for every DNS response.

    Other projects may likewise choose consensus for metadata or coordinators, but should justify the cost.

    Security connection

    Section titled “Security connection”

    Base Raft assumes crash/non-Byzantine replicas. A malicious participant that signs contradictory messages or intentionally violates the protocol is outside this failure model.

    Authenticated communication may protect node identity but does not transform crash-fault consensus into Byzantine-fault consensus.

    AI-era connection

    Section titled “AI-era connection”

    Multiple LLM agents “voting” on an answer is not equivalent to consensus. A production multi-agent platform may nevertheless rely on consensus underneath for task ownership, durable workflow state, membership, or coordination.

    This is a useful distinction between application-level decision heuristics and infrastructure agreement guarantees.

    Final-project connection

    Section titled “Final-project connection”

    After Ray removal, use consensus only when the problem actually requires one authoritative replicated order.

    A design record should answer:

    • what state requires consensus;
    • why weaker replication is insufficient;
    • how many replicas/which failure tolerance is required;
    • what happens in a minority partition;
    • what remains outside consensus, especially client retries and cross-shard work.

    Implementing Raft alone does not satisfy the entire final project. The consensus mechanism must support a meaningful application whose failure, recovery, observability, and correctness properties are experimentally demonstrated.
