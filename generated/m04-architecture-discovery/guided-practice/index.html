Naming, Discovery, and Decentralized Lookup — Guided Practice

Core practice: Complete cases 1, 4, 5, 7, 10, 11, and 12. Then use the Practice target at the end of this page as the stop criterion. The remaining cases are a reusable retrieval/challenge bank, not a checklist you must finish before the lab.

Complete these exercises before the main laboratory. For every architecture, mark state ownership and failure consequences rather than drawing boxes only.

1. Separate name, ID, address, and incarnation

Section titled “1. Separate name, ID, address, and incarnation”

Classify each item:

orders.service
worker-17
10.0.0.31:7000
process PID 2241
incarnation 9
sha256:8b1...

Then answer which values should survive:

  • process restart;
  • migration to a new host;
  • scale-out to three replicas;
  • complete replacement of one instance.

2. Replace a hard-coded endpoint

Section titled “2. Replace a hard-coded endpoint”

A client contains:

WORKER = "10.0.0.7:7000"

Redesign this into a logical service lookup.

Your design must state:

  1. the logical service name;
  2. where membership is stored;
  3. who updates it;
  4. how clients refresh it;
  5. what happens if lookup is unavailable;
  6. how a client reacts to one stale endpoint.

3. Architecture comparison

Section titled “3. Architecture comparison”

A job-processing service can be built as:

A. client → coordinator → workers
B. client → replicated coordinators → workers
C. clients/workers coordinate peer-to-peer

For each architecture, identify:

  • central state;
  • membership mechanism;
  • scheduling responsibility;
  • single-node failure consequence;
  • complexity introduced by the design.

Do not rank C as “best” simply because it is decentralized.

4. DNS cache timeline

Section titled “4. DNS cache timeline”

An address record has TTL 60 s.

t=0   client C1 resolves old address A
t=10  authority changes service to address B
t=20  new client C2 resolves
t=40  C1 sends another request
t=61  C1 resolves again

For each event, state which address each client may reasonably use.

Then explain why stale C1 behavior before expiry does not automatically mean the authoritative DNS server is broken.

5. Registration lease

Section titled “5. Registration lease”

A worker refreshes a 15-second lease every five seconds.

The last successful refresh occurs at 12:00:10.

The worker remains alive but becomes partitioned from the registry at 12:00:12.

Clients can still reach the worker directly.

  1. When may the registry expire the entry under the simple lease policy?
  2. Is the worker dead?
  3. Is the registry wrong to remove it?
  4. What availability trade-off does this create?
  5. What additional evidence could the system use?

6. Health is not one Boolean

Section titled “6. Health is not one Boolean”

For each condition, decide whether these checks should pass:

process-alive
port-listening
basic-readiness
full-dependency-readiness

Conditions:

  • process alive, database unavailable;
  • process overloaded but responding slowly;
  • replica alive but far behind the leader;
  • worker alive but cannot reach the registry;
  • worker alive and ready but one optional dependency is down.

There is no universal answer. Explain what each health signal is intended to authorize.

7. Stale client after worker death

Section titled “7. Stale client after worker death”

Registry state initially:

[A, B, C]

Client caches the list for 30 seconds. B crashes after five seconds. The registry detects and removes B after ten seconds.

Construct a timeline showing that the registry can be correct while the client still selects B.

Then combine Chapter 4 mechanisms to make the client robust without requiring instant membership convergence.

8. Compare balancing policies

Section titled “8. Compare balancing policies”

Three workers have capacities:

A = 1 unit
B = 1 unit
C = 8 units

Analyze:

  • pick first;
  • round robin;
  • uniform random;
  • weighted round robin;
  • least outstanding requests.

For each policy, state:

  • required information;
  • sensitivity to stale state;
  • likely behavior for unequal capacity.

9. Client-side versus proxy-side balancing

Section titled “9. Client-side versus proxy-side balancing”

Draw both designs.

Then compare them across:

  • client complexity;
  • number of network hops;
  • centralized infrastructure;
  • policy rollout;
  • observability;
  • registry dependency.

Identify one project from the final catalog where each approach could be reasonable.

10. Registry failure

Section titled “10. Registry failure”

A client currently has a cached healthy endpoint list.

The registry crashes.

Should the client stop serving requests immediately?

Answer for two architectures:

  1. cached endpoints are permitted until their TTL expires;
  2. every request requires a fresh registry lookup.

Explain what the architectural difference says about control-plane coupling.

11. Incarnation reasoning

Section titled “11. Incarnation reasoning”

Worker W7 starts with incarnation 12 and endpoint :7007.

It crashes and restarts as incarnation 13 on :7017.

A delayed heartbeat from incarnation 12 arrives after incarnation 13 has registered.

What should the registry do?

Explain why storing only node_id=W7 is insufficient to distinguish this execution.

12. Discovery is not authority

Section titled “12. Discovery is not authority”

A client caches:

leader → node A

The replicated system elects node B as the new leader, but the client’s cache has not refreshed.

Explain why the client may still contact A and why A must not accept an operation merely because discovery directed the client there.

Which later course mechanism establishes leadership authority?

13. Microservice boundary critique

Section titled “13. Microservice boundary critique”

A proposed architecture splits one program into eight services because “microservices scale better.”

For each new boundary, require the designer to answer:

  • What independently scales?
  • What state boundary exists?
  • What failure isolation is gained?
  • What deployment independence is gained?
  • Which new remote-call failure modes are introduced?

Recommend merging at least one pair of services if no meaningful independent responsibility exists.

14. AI-audited architecture review

Section titled “14. AI-audited architecture review”

Ask an AI assistant to review this design:

“All workers register once at startup. Clients cache the registry response forever. If an RPC fails, they retry the same address until it succeeds.”

Classify each AI finding as valid, invalid, or incomplete.

Then add at least one distributed-systems failure mode not identified by the assistant.

Practice target

Section titled “Practice target”

Before the laboratory, you should be able to explain this chain without using the words “magic” or “automatically”:

logical service name
        ↓
resolution / registry state
        ↓
possibly stale endpoint set
        ↓
selection policy
        ↓
RPC attempt
        ↓
runtime evidence and possible refresh

The important conclusion is that discovery provides candidate locations, not perfect knowledge.
