    Core practice: Complete cases 0a, 0b, 1, 2, 4, 5, 8, 10, 17, and 19. Then use the Practice target at the end of this page as the stop criterion. The remaining cases are a reusable retrieval/challenge bank, not a checklist you must finish before the lab.

    Complete these before the lab. Begin with operational evidence, then widen the model to adversarial behavior. For every proposed security mechanism, state exactly which threat it addresses and which threats remain.

    0a. Tail-latency diagnosisCore

    Section titled “0a. Tail-latency diagnosis”

    A service reports:

    throughput: stable
CPU: 42%
p50 latency: 18 ms
p95 latency: 90 ms
p99 latency: 1400 ms
queue depth: steadily increasing
retry rate: increasing

    List at least three competing hypotheses.

    For each hypothesis, name one additional observation that could support or reject it.

    Do not answer only “add more CPU.”

    0b. Trace reconstructionCore

    Section titled “0b. Trace reconstruction”

    Three services emit these events for request 81:

    api      start 81 t=0
worker   start 81 t=12
storage  start 81 t=18
storage  end   81 t=420
worker   end   81 t=430
api      end   81 t=435

    Where is most of the observed latency?

    Now remove the request IDs. Explain why timestamp proximity alone is not enough when many requests overlap.

    0c. Backpressure decisionChallenge bank

    Section titled “0c. Backpressure decision”

    A queue grows from 10 to 10,000 items while consumers remain at fixed capacity.

    Compare:

    • accepting everything;
    • bounding the queue and rejecting/deferring work;
    • increasing retries;
    • reducing upstream admission.

    Which choices reduce hidden work? Which change user-visible availability? State the trade rather than calling one universally correct.

    1. Threat-model a serviceCore

    Section titled “1. Threat-model a service”

    Choose one earlier course service and list:

    • assets;
    • principals;
    • trusted components;
    • untrusted components;
    • attacker capabilities;
    • explicit out-of-scope assumptions.

    Avoid writing only “the attacker can hack the server.” Make capabilities concrete.

    2. Authentication versus authorizationCore

    Section titled “2. Authentication versus authorization”

    Construct one request that is:

    • unauthenticated;
    • authenticated but unauthorized;
    • authenticated and authorized but semantically invalid.

    Explain which layer rejects each request.

    3. Identity versus addressChallenge bank

    Section titled “3. Identity versus address”

    A service currently accepts internal calls from 10.0.0.8 because that address is “known to belong to worker-2.”

    Explain why this is a weak identity model. Propose a stronger service-identity mechanism.

    4. TLS boundaryCore

    Section titled “4. TLS boundary”

    For a TLS-protected RPC, classify these threats as addressed, partially addressed, or not addressed by TLS alone:

    • passive eavesdropping;
    • message modification in transit;
    • unauthorized but authenticated user action;
    • malicious server implementation;
    • replay at the application layer;
    • stolen server private key.

    5. Replay and request IDsCore

    Section titled “5. Replay and request IDs”

    A valid authenticated transfer request is captured and replayed later.

    Explain how durable request deduplication can help and what retention/lifetime assumptions still matter.

    6. Least privilegeChallenge bank

    Section titled “6. Least privilege”

    A build worker currently receives credentials that permit access to every repository, every artifact bucket, and cluster-administration APIs.

    Redesign the authority model so the worker has only the permissions necessary for one job.

    7. Secret-handling auditChallenge bank

    Section titled “7. Secret-handling audit”

    Classify the following as safe to log, unsafe to log, or context-dependent:

    • request ID;
    • bearer token;
    • password;
    • certificate fingerprint;
    • full client certificate;
    • user email;
    • object key;
    • private key;
    • authorization decision.

    Explain your reasoning.

    8. Byzantine equivocationCore

    Section titled “8. Byzantine equivocation”

    Replica R3 tells R1 that value X was chosen and tells R2 that value Y was chosen.

    Why is this outside the ordinary Raft crash-fault model? What additional protocol properties are needed in a Byzantine setting?

    9. BFT replica countChallenge bank

    Section titled “9. BFT replica count”

    Using the classic relation:

    n >= 3f + 1

    compute the minimum number of replicas needed to tolerate:

    • f = 1;
    • f = 2;
    • f = 3.

    Explain why stronger failure tolerance requires more replicas than crash-fault majority consensus.

    10. Signatures versus agreementCore

    Section titled “10. Signatures versus agreement”

    All messages are digitally signed. Can two honest replicas still disagree on the final value?

    Explain why signatures prove message origin/integrity but do not themselves implement consensus.

    11. Sybil thought experimentChallenge bank

    Section titled “11. Sybil thought experiment”

    A protocol decides by “one identity, one vote,” and anyone may create an identity for free.

    Explain the attack and why controlled membership or another resource/admission mechanism is necessary.

    12. Permissioned versus permissionlessChallenge bank

    Section titled “12. Permissioned versus permissionless”

    Compare the membership assumptions of:

    • a university-owned five-node cluster;
    • a federation of independently administered institutions;
    • an open global network.

    Which identity/adversary questions differ?

    13. Workload isolation versus result trustChallenge bank

    Section titled “13. Workload isolation versus result trust”

    A tournament worker executes untrusted player code inside a container.

    Explain separately:

    • what the container protects;
    • what it does not establish about the correctness of the result returned by the worker.

    14. Agent tool delegationChallenge bank

    Section titled “14. Agent tool delegation”

    A user authorizes an AI agent to read calendar events but not send invitations.

    Design the authorization boundary so the tool service—not the model prompt—enforces this distinction.

    15. Agent retry ambiguityChallenge bank

    Section titled “15. Agent retry ambiguity”

    An agent invokes a payment tool. The payment commits, but the response times out.

    List the distributed/security fields and mechanisms needed for a safe retry.

    16. Internal-service trustChallenge bank

    Section titled “16. Internal-service trust”

    An internal storage service accepts all requests from the cluster network without authentication because “only trusted machines can reach it.”

    Identify at least three ways that assumption can fail and propose a better boundary.

    17. Resource exhaustionCore

    Section titled “17. Resource exhaustion”

    Construct an attack that uses valid requests to exhaust:

    • connection slots;
    • memory queues;
    • expensive fan-out;
    • retry capacity.

    Connect each to Chapter 12 overload controls.

    18. BFT cost comparisonChallenge bank

    Section titled “18. BFT cost comparison”

    Compare crash-fault replication and Byzantine-fault replication in terms of:

    • replica count;
    • messages;
    • authentication/verification;
    • implementation complexity;
    • deployment assumptions.

    Do not conclude that one is universally “better.”

    19. Trust tableCore

    Section titled “19. Trust table”

    Create a table for one final-project architecture:

    Component Trusted? Identity Authority Failure/adversary model

    Identify the most dangerous hidden assumption.

    20. AI-audited security reviewChallenge bank

    Section titled “20. AI-audited security review”

    Ask an AI assistant to security-review one architecture. Classify each suggestion as:

    • valid and in scope;
    • valid but out of scope;
    • vague/non-testable;
    • incorrect;
    • already mitigated.

    Then convert one valid suggestion into a precise testable security property.

    Practice target

    Section titled “Practice target”

    You are ready for the lab when you can explain all five distinctions:

    address != identity
identity != authority
TLS != authorization
signature != consensus
crash-fault tolerance != Byzantine tolerance
