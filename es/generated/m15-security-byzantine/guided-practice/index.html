    Práctica esencial: Completa los casos 0a, 0b, 1, 2, 4, 5, 8, 10, 17 y 19. Después usa el Objetivo de práctica al final de esta página como criterio para detenerte. Los casos restantes forman un banco reutilizable de recuperación/reto, no una lista que debas terminar antes del laboratorio.

    Completa estos ejercicios antes del laboratorio. Empieza por evidencia operacional y después amplía el modelo hacia comportamiento adversarial. Para cada mecanismo de seguridad propuesto, indica exactamente qué amenaza aborda y cuáles permanecen.

    0a. Diagnóstico de latencia de colaEsencial

    Sección titulada «0a. Diagnóstico de latencia de cola»

    Un servicio informa:

    rendimiento: estable
CPU: 42 %
latencia p50: 18 ms
latencia p95: 90 ms
latencia p99: 1400 ms
profundidad de cola: crece de forma sostenida
tasa de reintentos: creciente

    Enumera al menos tres hipótesis competidoras.

    Para cada una, nombra una observación adicional que pueda apoyarla o descartarla.

    No respondas solo «añadir CPU».

    0b. Reconstrucción de una trazaEsencial

    Sección titulada «0b. Reconstrucción de una traza»

    Tres servicios emiten estos eventos para la solicitud 81:

    api      start 81 t=0
worker   start 81 t=12
storage  start 81 t=18
storage  end   81 t=420
worker   end   81 t=430
api      end   81 t=435

    ¿Dónde se concentra la mayor parte de la latencia observada?

    Elimina ahora los IDs de solicitud. Explica por qué la proximidad de timestamps no basta cuando muchas solicitudes se solapan.

    0c. Decisión de control de presiónBanco de retos

    Sección titulada «0c. Decisión de control de presión»

    Una cola crece de 10 a 10 000 elementos mientras los consumidores mantienen capacidad fija.

    Compara:

    • aceptar todo;
    • acotar la cola y rechazar/diferir trabajo;
    • aumentar reintentos;
    • reducir admisión aguas arriba.

    ¿Qué opciones reducen trabajo oculto? ¿Cuáles cambian disponibilidad visible? Declara el compromiso en lugar de llamar a una opción universalmente correcta.

    1. Construye el threat model de un servicioEsencial

    Sección titulada «1. Construye el threat model de un servicio»

    Elige un servicio de capítulos anteriores y enumera:

    • activos;
    • principales/roles;
    • componentes de confianza;
    • componentes no confiables;
    • capacidades del atacante;
    • supuestos explícitos fuera de alcance.

    Evita «el atacante puede hackear el servidor». Define capacidades concretas.

    2. Autenticación frente a autorizaciónEsencial

    Sección titulada «2. Autenticación frente a autorización»

    Construye una solicitud que sea:

    • no autenticada;
    • autenticada, pero no autorizada;
    • autenticada y autorizada, pero semánticamente inválida.

    Explica qué capa rechaza cada una.

    3. Identidad frente a direcciónBanco de retos

    Sección titulada «3. Identidad frente a dirección»

    Un servicio acepta llamadas internas desde 10.0.0.8 porque esa dirección «pertenece a worker-2».

    Explica por qué es una identidad débil. Propón un mecanismo más fuerte de identidad de servicio.

    4. Límite de TLSEsencial

    Sección titulada «4. Límite de TLS»

    Para un RPC protegido con TLS, clasifica estas amenazas como abordadas, parcialmente abordadas o no abordadas por TLS por sí solo:

    • escucha pasiva;
    • modificación de mensajes en tránsito;
    • acción no autorizada de un usuario autenticado;
    • implementación maliciosa del servidor;
    • replay a nivel de aplicación;
    • robo de la clave privada del servidor.

    5. Replay e IDs de solicitudEsencial

    Sección titulada «5. Replay e IDs de solicitud»

    Se captura una solicitud de transferencia válida y autenticada y se reproduce más tarde.

    Explica cómo puede ayudar la deduplicación durable por ID de solicitud y qué supuestos de retención/vida siguen importando.

    6. Mínimo privilegioBanco de retos

    Sección titulada «6. Mínimo privilegio»

    Un worker de build recibe credenciales para todos los repositorios, todos los buckets y APIs de administración del clúster.

    Rediseña la autoridad para que ese worker tenga únicamente los permisos necesarios para un trabajo.

    7. Auditoría de secretos en logsBanco de retos

    Sección titulada «7. Auditoría de secretos en logs»

    Clasifica como seguro, inseguro o dependiente del contexto:

    • ID de solicitud;
    • bearer token;
    • contraseña;
    • fingerprint de certificado;
    • certificado completo del cliente;
    • email de usuario;
    • clave de objeto;
    • clave privada;
    • decisión de autorización.

    Explica.

    8. Equivocación bizantinaEsencial

    Sección titulada «8. Equivocación bizantina»

    R3 dice a R1 que fue elegido X y a R2 que fue elegido Y.

    ¿Por qué queda fuera del modelo crash-fault de Raft? ¿Qué propiedades adicionales se necesitan en un entorno bizantino?

    9. Número de réplicas BFTBanco de retos

    Sección titulada «9. Número de réplicas BFT»

    Usando:

    n >= 3f + 1

    calcula el mínimo para tolerar:

    • f=1;
    • f=2;
    • f=3.

    Explica por qué tolerar fallos más fuertes exige más réplicas que consenso por mayoría ante crashes.

    10. Firmas frente a acuerdoEsencial

    Sección titulada «10. Firmas frente a acuerdo»

    Todos los mensajes están firmados digitalmente. ¿Pueden dos réplicas honestas discrepar aún sobre el valor final?

    Explica por qué las firmas prueban origen/integridad, pero no implementan consenso.

    11. Experimento mental SybilBanco de retos

    Sección titulada «11. Experimento mental Sybil»

    Un protocolo decide «una identidad, un voto» y cualquiera puede crear identidades gratis.

    Explica el ataque y por qué hace falta membresía controlada u otro mecanismo de admisión/peso.

    12. Permissioned frente a permissionlessBanco de retos

    Sección titulada «12. Permissioned frente a permissionless»

    Compara supuestos de membresía de:

    • un clúster universitario de cinco nodos;
    • una federación de instituciones administradas independientemente;
    • una red global abierta.

    ¿Qué preguntas de identidad/adversario cambian?

    13. Aislamiento de workload frente a confianza en el resultadoBanco de retos

    Sección titulada «13. Aislamiento de workload frente a confianza en el resultado»

    Un worker de torneo ejecuta código no confiable dentro de un contenedor.

    Explica por separado:

    • qué protege el contenedor;
    • qué no demuestra sobre la corrección del resultado que devuelve el worker.

    14. Delegación de herramientas de un agenteBanco de retos

    Sección titulada «14. Delegación de herramientas de un agente»

    Un usuario autoriza a un agente a leer eventos del calendario, pero no a enviar invitaciones.

    Diseña el límite de autorización para que el servicio de herramientas —no el prompt— haga cumplir esa diferencia.

    15. Ambigüedad de reintento en agentesBanco de retos

    Sección titulada «15. Ambigüedad de reintento en agentes»

    Un agente llama una herramienta de pago. El pago se confirma, pero la respuesta expira.

    Enumera campos y mecanismos de seguridad/distribución necesarios para un reintento seguro.

    16. Confianza en servicios internosBanco de retos

    Sección titulada «16. Confianza en servicios internos»

    Un almacenamiento interno acepta toda solicitud de la red del clúster sin autenticar porque «solo máquinas de confianza pueden alcanzarlo».

    Identifica tres formas en que puede fallar el supuesto y propón un límite mejor.

    17. Agotamiento de recursosEsencial

    Sección titulada «17. Agotamiento de recursos»

    Construye un ataque con solicitudes válidas que agote:

    • conexiones;
    • memoria de colas;
    • fan-out costoso;
    • capacidad de reintento.

    Conecta cada uno con controles de sobrecarga.

    18. Coste BFTBanco de retos

    Sección titulada «18. Coste BFT»

    Compara replicación crash-fault y Byzantine-fault en:

    • número de réplicas;
    • mensajes;
    • autenticación/verificación;
    • complejidad;
    • supuestos de despliegue.

    No concluyas que una sea universalmente «mejor».

    19. Tabla de confianzaEsencial

    Sección titulada «19. Tabla de confianza»

    Crea para un proyecto final:

    Componente ¿Confiable? Identidad Autoridad Modelo de fallo/adversario

    Identifica el supuesto oculto más peligroso.

    20. Revisión de seguridad auditada con IABanco de retos

    Sección titulada «20. Revisión de seguridad auditada con IA»

    Pide a un asistente revisar una arquitectura. Clasifica cada sugerencia como:

    • válida y dentro del alcance;
    • válida, pero fuera del alcance;
    • vaga/no verificable;
    • incorrecta;
    • ya mitigada.

    Convierte después una sugerencia válida en una propiedad de seguridad precisa y comprobable.

    Objetivo de práctica

    Sección titulada «Objetivo de práctica»

    Estás preparado cuando puedas explicar:

    dirección != identidad
identidad != autoridad
TLS != autorización
firma != consenso
tolerancia crash-fault != tolerancia bizantina
