    Por qué importa este capítulo

    Sección titulada «Por qué importa este capítulo»

    Antes de elegir un runtime decide dónde vive cada responsabilidad. Dos sistemas pueden exponer la misma API y, sin embargo, colocar estado, descubrimiento, scheduling y recuperación en lugares completamente distintos.

    Usa durante todo el capítulo estas preguntas:

    • ¿quién posee el estado autoritativo?
    • ¿quién inicia la comunicación?
    • ¿quién descubre a quién?
    • ¿quién decide dónde ejecutar trabajo?
    • ¿qué puede fallar de forma independiente?
    • ¿qué responsabilidad pertenece a la aplicación y cuál al middleware?

    Ray será nuestro ejemplo concreto de middleware. No es la definición de una arquitectura distribuida.

    1. Arquitectura primero: coloca responsabilidades

    Sección titulada «1. Arquitectura primero: coloca responsabilidades»

    Cliente/servidor

    Sección titulada «Cliente/servidor»
    cliente → servicio

    Se centraliza un rol, no necesariamente una máquina. Puede haber muchas réplicas detrás de un nombre lógico. Pregunta quién posee la decisión autoritativa para cada operación.

    Por capas o multicapa

    Sección titulada «Por capas o multicapa»
    cliente → API → capa de workers/servicios → estado

    Cada límite puede escalar y fallar de forma distinta. Una capa es útil cuando encapsula una responsabilidad coherente; es ruido si solo añade otro salto de red.

    Dirigida por eventos

    Sección titulada «Dirigida por eventos»
    productor → evento/cola → consumidor(es)

    El productor puede terminar antes de que un consumidor actúe. Por tanto, «aceptado», «entregado», «procesado» y «confirmado» dejan de significar lo mismo.

    Entre pares

    Sección titulada «Entre pares»
    peer A ↔ peer B ↔ peer C

    Descubrimiento, placement y membresía ya no pueden suponerse responsabilidad de un servidor permanente.

    Los sistemas híbridos son normales

    Sección titulada «Los sistemas híbridos son normales»

    Un plano de datos P2P puede depender de identidad centralizada. Microservicios pueden usar eventos y RPC al mismo tiempo. No etiquetes el sistema con una sola palabra y dejes de razonar.

    Detente y predice. Necesitas workers dinámicos, estado durable de trabajos y consultas de estado de baja latencia. ¿Qué responsabilidad centralizarías primero y cuál puede permanecer distribuida sin crear coordinación innecesaria?

    Cuando el mapa de responsabilidades está claro, puedes evaluar exactamente qué cajas, canales y políticas implementa el middleware.

    2. Middleware entre intención y mecanismo

    Sección titulada «2. Middleware entre intención y mecanismo»

    La aplicación quiere decir:

    ejecuta F en recursos disponibles y entrégame el resultado más tarde

    Sin middleware tendría que resolver algo como:

    descubrir workers
      ↓
elegir endpoint
      ↓
serializar argumentos
      ↓
enviar solicitud
      ↓
seguir identidad del trabajo
      ↓
ejecutar
      ↓
representar/guardar resultado
      ↓
manejar crash o timeout
      ↓
recuperar resultado

    El middleware ofrece una abstracción más alta.

    abstracción de aplicación ≠ mecanismo subyacente

    Una API no elimina red, serialización, scheduling, procesos o fallos. Solo delega su mecanismo/política.

    Mantén una pregunta visible:

    ¿Qué responsabilidad acabo de delegar?

    3. Hilo histórico: ocultar la red sin olvidar sus consecuencias

    Sección titulada «3. Hilo histórico: ocultar la red sin olvidar sus consecuencias»

    RPC hizo que la interacción remota se pareciera a una llamada. CORBA y Java RMI extendieron la idea a objetos remotos. MPI eligió comunicación explícita. MapReduce y Spark delegaron scheduling y movimiento de datos. Runtimes generales como Ray exponen pocas primitivas de alto nivel.

    La tensión se repite:

    abstracción más cómoda
        ↕
más comportamiento delegado al runtime

    El objetivo no es rechazar abstracciones; es conocer su contrato y sus límites.

    4. Modelo mental de Ray Core

    Sección titulada «4. Modelo mental de Ray Core»
    Driver / proceso de aplicación
          │
          ├── envía Tasks
          ├── crea Actors
          └── conserva ObjectRefs
                    │
              runtime de Ray
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       worker     actor     worker
       process    process    process
          │         │         │
          └──── objetos remotos ────┘
    • Driver: programa que inicializa Ray y envía trabajo.
    • Task: función remota asíncrona.
    • Actor: worker con identidad y estado asociado a una clase remota.
    • ObjectRef: referencia a un resultado/objeto que quizá todavía no está localmente disponible.
    • Runtime/cluster: workers, scheduling, objetos, procesos, metadatos y políticas de fallo.

    Son abstracciones de programación. Más adelante sustituirás solo las que tu sistema necesite.

    5. Una task no es simplemente «llamar esta IP»

    Sección titulada «5. Una task no es simplemente «llamar esta IP»»
    @ray.remote
def transform(x):
    return x + 1

ref = transform.remote(41)

    La aplicación no indicó dirección de worker, conexión TCP, formato de serialización, request ID, endpoint de resultado, cola ni bucle de reintento.

    El runtime recibe trabajo y el scheduler elige dónde ejecutarlo según recursos lógicos, estrategia y otros factores.

    Compara:

    RPC:
el cliente elige un servicio/endpoint y llama una operación

Ray task:
la aplicación envía trabajo; el runtime elige un worker adecuado

    La diferencia útil es quién posee la decisión de placement.

    6. .remote() cambia lugar y tiempo

    Sección titulada «6. .remote() cambia lugar y tiempo»

    Llamada ordinaria:

    value = transform(41)

    Llamada remota:

    ref = transform.remote(41)

    La segunda devuelve una referencia y separa envío de finalización.

    submit A ─────┐
              ├─ posible ejecución concurrente
submit B ─────┘
       ↓
esperar cuando los valores sean necesarios

    No existe speedup «por usar Ray». Existe concurrencia cuando el grafo contiene trabajo independiente y hay recursos para ejecutarlo.

    7. ObjectRef es una future distribuida

    Sección titulada «7. ObjectRef es una future distribuida»
    ref = work.remote(data)

    puede leerse como:

    ObjectRef
   │
   └── “valor producido por este trabajo remoto”

    Solo cuando necesitas materializarlo llamas, por ejemplo:

    value = ray.get(ref)

    La referencia puede formar parte de otro trabajo sin que el driver tenga que descargar y reenviar el valor.

    Error común de rendimiento

    Sección titulada «Error común de rendimiento»

    Expone concurrencia:

    refs = [work.remote(x) for x in values]
results = ray.get(refs)

    Puede serializar:

    results = []
for x in values:
    results.append(ray.get(work.remote(x)))

    Predice: cuatro tasks de un segundo y cuatro workers. ¿Qué diferencia esperas? Después mídela.

    8. ray.wait y finalización parcial

    Sección titulada «8. ray.wait y finalización parcial»

    No siempre quieres esperar todos los resultados.

    refs = [A, B, C, D]

termina primero: C
después:          A
en curso:         B, D

    Separar envío y finalización sirve para progreso incremental, trabajo especulativo, limitar solicitudes en vuelo o responder con resultados disponibles.

    La idea excede a Ray: futures, colas y job IDs usan la misma separación.

    9. El movimiento de datos no desaparece

    Sección titulada «9. El movimiento de datos no desaparece»

    Aunque no llames send(), los bytes deben estar donde se ejecuta el trabajo.

    Pregunta siempre:

    ¿mover cálculo hacia los datos?
        o
¿mover datos hacia el cálculo?

    Esta pregunta reaparece en bases distribuidas, object stores, búsqueda fragmentada, ML y sistemas edge.

    No deduzcas número de copias o coste físico desde la sintaxis. Obsérvalo o decláralo como supuesto.

    10. Actors: estado local con identidad

    Sección titulada «10. Actors: estado local con identidad»
    @ray.remote
class Counter:
    def __init__(self):
        self.value = 0

    def increment(self):
        self.value += 1
        return self.value

    Un actor hace natural modelar coordinadores, registros, modelos cargados, caches, shards o participantes con estado.

    Pero:

    abstracción con estado ≠ estado durable y replicado

    Si el proceso actor desaparece, su memoria no se vuelve durable mágicamente. Si el estado importa tras un crash, tu diseño debe persistirlo o reconstruirlo.

    11. Serialización del actor no significa orden global

    Sección titulada «11. Serialización del actor no significa orden global»

    Un actor ordinario puede ejecutar sus métodos con un modelo que simplifica el acceso a su estado local.

    No extrapoles:

    «Los actores garantizan un único orden global».

    Varios actores, clientes concurrentes y tasks independientes siguen generando problemas distribuidos de orden.

    12. Identidad del actor y proceso worker no son lo mismo

    Sección titulada «12. Identidad del actor y proceso worker no son lo mismo»

    Distingue:

    proceso físico/del runtime
          ≠
identidad lógica del actor

    La misma distinción aparecerá entre proceso y nodo Raft, contenedor y servicio, máquina y shard.

    13. Scheduling: una decisión delegada

    Sección titulada «13. Scheduling: una decisión delegada»

    Al enviar trabajo alguien debe responder:

    ¿Dónde se ejecuta?

    Ray usa recursos lógicos como CPU, GPU o recursos personalizados.

    @ray.remote(num_cpus=2)
def expensive_job(x):
    ...

    Esto restringe elegibilidad de scheduling. No es por sí solo aislamiento del sistema operativo.

    declaración de recursos → política de scheduling → placement

    es diferente de:

    aislamiento/enforcement de SO o contenedor

    14. Localidad frente a independencia de fallos

    Sección titulada «14. Localidad frente a independencia de fallos»

    Supón:

    Nodo A: 4 CPU
Nodo B: 4 CPU
Nodo C: 1 GPU + 4 CPU

    Una tarea GPU necesita un lugar compatible. Actores que se comunican mucho pueden beneficiarse de cercanía; réplicas cuyo objetivo es tolerar fallos pueden necesitar separación.

    localidad / menor coste de comunicación
               ↕
independencia de fallos / distribución de carga

    Este compromiso reaparece en almacenamiento replicado.

    15. La semántica de fallo forma parte del contrato

    Sección titulada «15. La semántica de fallo forma parte del contrato»

    Ray distingue, entre otras cosas, muerte inesperada de workers, excepciones de aplicación, reinicio de actors y reintentos configurables.

    No memorices una frase como «Ray reintenta». Pregunta:

    • ¿qué tipo de fallo?
    • ¿cuántos reintentos?
    • ¿se reinicia un actor?
    • ¿qué estado sobrevive?
    • ¿puede repetirse un efecto externo?

    Repetición segura y peligrosa

    Sección titulada «Repetición segura y peligrosa»

    Seguro:

    hash(data)
square(7)
thumbnail(immutable_input)

    Peligroso sin mecanismo adicional:

    charge(card)
send_email()
increment_external_counter()

    La corrección de un reintento depende de la semántica de la aplicación, no solo del runtime.

    16. Request identity e idempotencia reaparecerán

    Sección titulada «16. Request identity e idempotencia reaparecerán»

    Middleware puede reintentar trabajo, pero si el mismo efecto puede ejecutarse dos veces la aplicación necesita una estrategia: operación idempotente, clave estable, deduplicación, transacción u otro mecanismo.

    El Capítulo 4 hace explícita esta frontera mediante RPC.

    17. Éxito del runtime no es corrección de aplicación

    Sección titulada «17. Éxito del runtime no es corrección de aplicación»

    Una task puede terminar «OK» y producir un resultado lógicamente incorrecto.

    Un actor puede seguir vivo mientras su estado está desactualizado.

    Un reintento puede conseguir que una task termine y duplicar un efecto externo.

    Por eso debemos separar:

    salud/estado del runtime
       ≠
garantía de la aplicación

    18. Observabilidad: mira debajo de la abstracción

    Sección titulada «18. Observabilidad: mira debajo de la abstracción»

    Durante el laboratorio recoge PID, job/task IDs, tiempos, estado del actor y logs de aplicación.

    La pregunta no es «¿Ray dice SUCCESS?». Es «¿qué ejecución ocurrió y qué evidencia la reconstruye?».

    19. La observabilidad debe exponer la frontera de abstracción

    Sección titulada «19. La observabilidad debe exponer la frontera de abstracción»

    Ray ofrece información de runtime sobre tasks, actors y su estado de ejecución mediante herramientas de observabilidad, State APIs, logs y dashboard.

    Úsala para responder:

    • ¿qué proceso ejecutó esta task?
    • ¿se solaparon dos tasks en el tiempo?
    • ¿qué actor murió?
    • ¿se reintentó una task?
    • ¿dónde residía un objeto?
    • ¿qué recursos se solicitaron?

    Después compara lo que sabe el runtime con lo que sabe la aplicación.

    Por ejemplo:

    Runtime: el intento #2 de la task terminó correctamente
Aplicación: la solicitud R aparece dos veces en el log de auditoría externo

    Ambos hechos pueden ser verdaderos. Un diagnóstico correcto cruza la frontera de abstracción.

    20. Ejemplo trabajado — tasks secuenciales frente a paralelas

    Sección titulada «20. Ejemplo trabajado — tasks secuenciales frente a paralelas»

    Supón cuatro inputs independientes y una función que tarda aproximadamente un segundo.

    Python secuencial

    Sección titulada «Python secuencial»
    results = [slow(x) for x in range(4)]

    Forma aproximada de dependencias:

    A → B → C → D

    Envío remoto con get inmediato

    Sección titulada «Envío remoto con get inmediato»
    results = [ray.get(slow.remote(x)) for x in range(4)]

    Sigue siendo aproximadamente:

    A → espera → B → espera → C → espera → D

    Enviar todo y recoger después

    Sección titulada «Enviar todo y recoger después»
    refs = [slow.remote(x) for x in range(4)]
results = ray.get(refs)

    Forma de dependencias:

    A ─┐
B ─┼─ workers disponibles
C ─┼─ pueden ejecutar concurrentemente
D ─┘

    El laboratorio mide tiempo transcurrido y registra PIDs reales de workers para que puedas observar tanto concurrencia como scheduling.

    21. Ejemplo trabajado — ¿task o actor?

    Sección titulada «21. Ejemplo trabajado — ¿task o actor?»

    Supón que la aplicación cuenta trabajos procesados.

    Enfoque con task

    Sección titulada «Enfoque con task»
    @ray.remote
def process(job):
    return result

    Cada task puede ser conceptualmente independiente.

    Si el contador importa, otro servicio debe ser su propietario.

    Enfoque con actor

    Sección titulada «Enfoque con actor»
    @ray.remote
class Worker:
    def __init__(self):
        self.completed = 0

    def process(self, job):
        ...
        self.completed += 1

    Ahora el contador es estado local del actor.

    Aparecen inmediatamente preguntas:

    • ¿qué ocurre si muere el actor?
    • ¿debe sobrevivir el contador?
    • ¿un actor se convierte en cuello de botella?
    • ¿pueden varios actors tener contadores independientes?
    • ¿quién los agrega?

    La abstracción correcta depende de la semántica requerida para el estado.

    22. Ejemplo trabajado — dependencias ocultas en una aplicación Ray pequeña

    Sección titulada «22. Ejemplo trabajado — dependencias ocultas en una aplicación Ray pequeña»

    Considera:

    @ray.remote
def resize(image):
    return transformed

refs = [resize.remote(img) for img in images]
outputs = ray.get(refs)

    La lógica visible es pequeña.

    Un mapa de dependencias de middleware revela más:

    Requisito de aplicación Responsabilidad de Ray en Fase 1
    encontrar capacidad de ejecución scheduler / workers
    despachar trabajo runtime de tasks remotas
    serializar input serialización del runtime
    hacer accesible el input movimiento de objetos/datos
    representar resultado pendiente ObjectRef
    ejecutar concurrentemente scheduling de workers
    exponer crash de worker manejo de fallos de task
    recoger resultado recuperación de objeto
    observar estado de task logs/state/dashboard

    Esta tabla es uno de los artefactos más importantes de toda la metodología del proyecto final.

    23. El mapa de dependencias de middleware no es una lista de APIs de Ray

    Sección titulada «23. El mapa de dependencias de middleware no es una lista de APIs de Ray»

    Un mapa débil dice:

    usa ray.remote
usa ray.get
usa actors

    Un mapa útil empieza por requisitos:

    Requisito Mecanismo Ray Supuesto Pregunta para diseño nativo
    distribuir trabajos independientes tasks trabajos serializables ¿cómo se envían a workers?
    conservar estado local del worker actor el proceso del actor sigue siendo útil ¿debe ser durable el estado?
    elegir un worker scheduler los recursos declarados representan necesidad ¿qué política de scheduling hace falta?
    sobrevivir crash de worker retry de task repetir ejecución es seguro ¿cómo se manejarán duplicados?
    referirse a un resultado remoto ObjectRef runtime sigue la dependencia ¿dónde vivirán los resultados nativos?

    La cuarta columna se convierte en la agenda de diseño de la Fase 2.

    24. La Fase 1 del proyecto final debe optimizar aprendizaje, no sofisticación arquitectónica

    Sección titulada «24. La Fase 1 del proyecto final debe optimizar aprendizaje, no sofisticación arquitectónica»

    El propósito del prototipo Ray es comprender rápidamente el dominio.

    Una buena Fase 1:

    • implementa el camino funcional principal;
    • se ejecuta sobre varios workers o actors Ray;
    • demuestra al menos un comportamiento de fallo o concurrencia;
    • congela un contrato externo de comportamiento;
    • documenta dependencias de middleware;
    • identifica preguntas para el diseño nativo.

    Una mala Fase 1 dedica casi todo el esfuerzo a infraestructura avanzada específica de Ray que será eliminada inmediatamente.

    Mantén deliberadamente pequeño el prototipo Ray.

    25. La frontera de retirada de Ray es un ejercicio de diseño

    Sección titulada «25. La frontera de retirada de Ray es un ejercicio de diseño»

    Después de Fase 1 no traduces cada feature de Ray línea por línea.

    En su lugar:

    prototipo Ray
     ↓
contrato de comportamiento
     ↓
requisitos + mapa de dependencias
     ↓
alternativas arquitectónicas
     ↓
mínimos mecanismos nativos justificados

    Ejemplos:

    Fase 1 Posibilidad nativa en Fase 2
    task Ray operación explícita de worker por gRPC
    actor servicio Go de larga duración
    ObjectRef job ID + almacén de resultados
    scheduler Ray cola central / work stealing / asignación estática
    membership del runtime registro / gossip / bootstrap por configuración
    retries de tasks timeout, retry y deduplicación explícitos
    estado del actor base de datos persistente / log replicado / estado local

    Proyectos diferentes deben producir respuestas diferentes.

    Si todos los grupos recrean el mismo scheduler y registro genéricos, la metodología dejó de usar el dominio de la aplicación como restricción de diseño.

    26. Lo que Ray no debe enseñarte

    Sección titulada «26. Lo que Ray no debe enseñarte»

    «Distribuir es añadir un decorator»

    Sección titulada ««Distribuir es añadir un decorator»»

    El decorator elige una abstracción. El runtime sigue implementando muchos mecanismos distribuidos.

    «ObjectRef es almacenamiento durable»

    Sección titulada ««ObjectRef es almacenamiento durable»»

    Una referencia a un objeto remoto no proporciona automáticamente la garantía de durabilidad de la aplicación.

    «Actor significa servicio replicado»

    Sección titulada ««Actor significa servicio replicado»»

    Un actor es un worker remoto con estado, no una máquina de estados replicada por defecto.

    «Retries significa exactly-once»

    Sección titulada ««Retries significa exactly-once»»

    Repetir la ejecución puede repetir efectos secundarios.

    «Solicitar recursos equivale a seguridad/aislamiento»

    Sección titulada ««Solicitar recursos equivale a seguridad/aislamiento»»

    Los recursos de scheduling y la imposición de aislamiento por el sistema operativo son problemas distintos.

    «Si Ray lo maneja, no necesito entenderlo»

    Sección titulada ««Si Ray lo maneja, no necesito entenderlo»»

    El resto del curso existe precisamente para entender y construir explícitamente los mecanismos ocultos aquí.

    27. Curiosidad — un runtime puede recuperar un objeto recomputándolo

    Sección titulada «27. Curiosidad — un runtime puede recuperar un objeto recomputándolo»

    La intuición tradicional de almacenamiento dice:

    «Si se pierde la única copia, recupérala desde otra copia».

    Algunos runtimes de dataflow pueden hacer otra cosa:

    «Si recuerdo cómo se produjo este valor y los inputs siguen disponibles, puedo calcularlo de nuevo».

    Así, el historial de cómputo se convierte en mecanismo de recuperación.

    La idea aparece en sistemas de procesamiento de datos, build systems, motores de workflows y caches.

    También expone una condición: recomputar es mucho más fácil cuando el cálculo es determinista y repetible.

    28. Curiosidad — decisiones del middleware se convierten en semántica de aplicación durante los fallos

    Sección titulada «28. Curiosidad — decisiones del middleware se convierten en semántica de aplicación durante los fallos»

    En operación normal, dos runtimes con políticas de retry distintas pueden parecer idénticos.

    Ante un crash del worker:

    Runtime A: reintenta automáticamente la task
Runtime B: reporta el fallo inmediatamente

    Ahora la política del runtime cambia el comportamiento visible de la aplicación.

    Por eso los ingenieros de producción leen documentación de tolerancia a fallos, no solo tutoriales de API.

    29. Los agentes de programación con IA hacen todavía más importante la lección sobre abstracciones

    a:

    Pero la Fase 1 no termina hasta que puedas explicar cada capacidad del runtime relevante para el proyecto.

    Profundización — qué debe quedar visible detrás de la comodidad de Ray

    Sección titulada «Profundización — qué debe quedar visible detrás de la comodidad de Ray»

    La forma más útil de estudiar middleware no es memorizar APIs, sino reconstruir el camino real de una operación.

    Cuando escribes:

    ref = work.remote(input)

    la línea visible no te dice, por sí sola:

    • qué proceso recibió finalmente el trabajo;
    • qué metadata necesitó el scheduler para decidir placement;
    • si el input se serializó una vez o varias;
    • si los bytes viajaron desde el driver, desde otro worker o desde un object store del runtime;
    • cuántos intentos de ejecución ocurrieron;
    • qué estado del runtime sobreviviría a la muerte de un worker;
    • cómo se representaría el resultado si el proceso productor desapareciera.

    Ese inventario importa porque la Fase 2 tendrá que decidir cuáles de esas propiedades son realmente necesarias. Un servicio nativo pequeño quizá no necesite scheduler general: puede bastar una cola central o incluso una asignación estática. Otro proyecto puede necesitar afinidad por datos, prioridad o recursos heterogéneos. El criterio no es «recrear Ray», sino conservar las garantías relevantes con la arquitectura más pequeña que puedas justificar.

    Placement no es solo un detalle de rendimiento

    Sección titulada «Placement no es solo un detalle de rendimiento»

    Imagina dos decisiones válidas para el mismo actor con estado:

    A. colocar cerca de sus datos
B. colocar lejos de otra réplica para reducir fallo correlacionado

    A reduce coste de movimiento. B mejora independencia de fallos.

    El middleware puede elegir usando información y políticas que la aplicación no ve directamente. Por eso un benchmark sin registrar dónde ejecutó realmente cada tarea puede confundir una mejora de placement accidental con una propiedad general del diseño.

    En la versión nativa debes poder contestar:

    • ¿qué información usa la política?
    • ¿qué ocurre cuando el nodo preferido no está?
    • ¿la decisión es estable o puede cambiar entre intentos?
    • ¿qué parte de la corrección depende de esa ubicación?

    ObjectRef representa una dependencia, no una garantía de almacenamiento

    Sección titulada «ObjectRef representa una dependencia, no una garantía de almacenamiento»

    Una referencia remota resulta cómoda porque desacopla producción y consumo:

    producer task ──> ObjectRef ──> consumer task

    Pero el significado de aplicación depende de lo que ocurra con el valor subyacente. Un runtime puede conservar una copia, transferirla, reconstruirla a partir del linaje de cómputo o declarar el objeto perdido cuando ya no puede producirse otra vez.

    Esto obliga a separar tres conceptos:

    resultado disponible
resultado reconstruible
resultado durable según el contrato de la aplicación

    No son equivalentes. Un modelo entrenado que el usuario considera «guardado» necesita una frontera de durabilidad distinta a una salida temporal que puede recalcularse.

    El linaje solo ayuda cuando repetir el cómputo conserva la semántica

    Sección titulada «El linaje solo ayuda cuando repetir el cómputo conserva la semántica»

    La recomputación es poderosa para funciones puras:

    output = transform(input_inmutable)

    pero puede ser incorrecta si ejecutar otra vez produce efectos externos:

    reserve_ticket()
send_notification()
charge_account()

    Incluso cuando Ray puede volver a lanzar una task, la aplicación debe decidir si repetir esa task representa el mismo efecto lógico o uno nuevo.

    Esta observación conecta directamente con el Capítulo 4:

    retry de runtime
      ↓
nuevo intento de ejecución
      ↓
¿misma operación lógica?
      ↓
request_id + idempotencia/deduplicación

    Actors simplifican ownership local, pero crean preguntas de ciclo de vida

    Sección titulada «Actors simplifican ownership local, pero crean preguntas de ciclo de vida»

    Un actor permite decir con claridad:

    este estado pertenece a esta identidad lógica de worker.

    Eso es valioso. Pero todavía debes distinguir:

    identidad del actor
proceso que lo ejecuta ahora
estado en memoria
estado durable
réplicas de ese estado

    Si un actor reinicia, la clase puede reconstruirse con memoria vacía. Si el sistema necesita continuidad lógica, debe existir una historia de recuperación: cargar snapshot, reabrir almacenamiento, reconstruir desde eventos o consultar otra autoridad.

    También debes preguntar si serializar métodos del actor oculta una política de concurrencia que después deberás recrear explícitamente. Un actor que procesa una llamada a la vez puede hacer correcto un contador simplemente porque convierte todo acceso en secuencial. Al retirar Ray, varios handlers concurrentes de un servidor Go podrían reintroducir la carrera si no preservas el mismo invariante.

    La política de fallos debe observarse, no imaginarse

    Sección titulada «La política de fallos debe observarse, no imaginarse»

    Para una task concreta, registra:

    logical_job_id
runtime_task_id
attempt
worker_pid
start
end / failure
effect_id si existe

    Con esa evidencia puedes distinguir:

    • una task que nunca empezó;
    • una que falló a mitad;
    • una que terminó y fue reintentada;
    • dos intentos que produjeron un único efecto lógico;
    • dos intentos que produjeron efectos duplicados.

    Sin esta correlación, «Ray recuperó el trabajo» puede esconder comportamientos de aplicación muy distintos.

    Resumen del capítulo

    Sección titulada «Resumen del capítulo»

    Ray nos permite experimentar primero con un modelo compacto de programación distribuida antes de implementar directamente sus mecanismos.

    Las lecciones centrales son:

    1. El middleware delega responsabilidades distribuidas; no las elimina.
    2. Las tasks Ray expresan trabajo remoto asíncrono cuyo placement selecciona el runtime.
    3. ObjectRef separa envío/dependencia de disponibilidad local de un valor.
    4. Los actors proporcionan workers remotos con estado, no estado automáticamente durable o replicado.
    5. Placement y movimiento de datos siguen importando aunque el código no envíe bytes explícitamente.
    6. Los recursos lógicos influyen en scheduling y son distintos del aislamiento fuerte de recursos.
    7. La semántica de fallo y retry forma parte del contrato del middleware.
    8. Retry automático puede duplicar efectos secundarios de aplicación.
    9. Éxito del runtime y corrección de aplicación son afirmaciones distintas.
    10. El mapa de dependencias convierte comodidad en Fase 1 en preguntas de diseño para Fase 2.
    11. Ray se elimina deliberadamente tras el prototipo para que seas responsable de los mecanismos requeridos.

    La progresión deseada es:

    «Puedo distribuir esto con Ray».
              ↓
«Puedo explicar qué proporcionó Ray».
              ↓
«Sé cuáles de esos mecanismos necesita realmente mi problema».
              ↓
«Puedo construir y defender esos mecanismos sin Ray».
