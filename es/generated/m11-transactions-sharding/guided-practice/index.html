    Práctica esencial: Completa los casos 1, 5, 6, 8, 9, 10, 12, 16 y 17. Después usa el Objetivo de práctica al final de esta página como criterio para detenerte. Los casos restantes forman un banco reutilizable de recuperación/reto, no una lista que debas terminar antes del laboratorio.

    Completa estos ejercicios antes del laboratorio. Para cada escenario, identifica primero el límite de propiedad y solo después decide si realmente hace falta coordinación.

    1. Replicación frente a shardingEsencial

    Sección titulada «1. Replicación frente a sharding»

    Dibuja:

    1. un dataset lógico con tres réplicas;
    2. un dataset lógico dividido en tres shards;
    3. tres shards, cada uno con tres réplicas.

    Para cada diagrama explica qué problema de fallos o escalado resuelve.

    2. Elige una clave de particiónBanco de retos

    Sección titulada «2. Elige una clave de partición»

    Un servicio de calendario permite:

    • listar eventos de un usuario;
    • crear un evento privado;
    • invitar a varios usuarios a una reunión;
    • buscar disponibilidad de un grupo.

    Compara particionar por:

    • ID de evento;
    • ID de usuario;
    • rango de fechas.

    ¿Qué operaciones quedan locales y cuáles cruzan shards?

    3. Hot keyBanco de retos

    Sección titulada «3. Hot key»

    Diez millones de usuarios se distribuyen uniformemente mediante hash, pero una cuenta famosa recibe el 25 % de todas las lecturas.

    ¿Por qué equilibrar claves no equivale a equilibrar carga? Propón dos mitigaciones e indica si preservan orden fuerte para las escrituras de ese usuario.

    4. Coste local frente a coste entre shardsBanco de retos

    Sección titulada «4. Coste local frente a coste entre shards»

    Una operación local requiere 2 ms de routing y 6 ms de commit del shard.

    Una operación entre dos shards los contacta en paralelo, cada uno tarda 6 ms, y además usa dos fases del coordinador de 3 ms y 2 ms de routing.

    Estima la latencia idealizada ignorando colas. Después explica por qué la latencia p95/p99 real puede ser peor que esta aritmética.

    5. Invariante de transferenciaEsencial

    Sección titulada «5. Invariante de transferencia»

    Para:

    A=100 en shard 1
B=50 en shard 2
TRANSFER 20 A→B

    enumera todos los estados finales externamente visibles que serían inválidos si se exige una transferencia atómica.

    6. Traza de mensajes 2PCEsencial

    Sección titulada «6. Traza de mensajes 2PC»

    Escribe la secuencia completa de una transacción T9 satisfactoria entre coordinador C y participantes A/B.

    Marca cuándo cada participante entra en PREPARED y cuándo el COMMIT global se vuelve autoritativo.

    7. PREPARE duplicadoBanco de retos

    Sección titulada «7. PREPARE duplicado»

    A recibe PREPARE T9 dos veces porque se perdió la primera respuesta YES.

    ¿Qué estado debe conservar A para que la segunda solicitud no reserve ni debite dos veces?

    8. Ventanas de crash del coordinadorEsencial

    Sección titulada «8. Ventanas de crash del coordinador»

    Para cada punto indica qué saben A y B y si pueden confirmar, abortar o deben esperar:

    1. el coordinador cae antes de cualquier PREPARE;
    2. A votó YES y B nunca vio la transacción;
    3. A y B votaron YES y no existe decisión durable;
    4. existe COMMIT durable, pero nadie lo recibió;
    5. A confirmó y B sigue PREPARED.

    9. Error conceptual sobre timeoutEsencial

    Sección titulada «9. Error conceptual sobre timeout»

    Un participante votó YES y lleva 30 segundos esperando.

    Explica por qué esta regla puede romper atomicidad:

    if wait > 30s:
    abort

    10. 2PC frente a consensoEsencial

    Sección titulada «10. 2PC frente a consenso»

    A y B son grupos Raft replicados.

    Dibuja dónde opera Raft y dónde opera 2PC para una transacción entre shards. Explica por qué sustituir uno por el otro cambia el problema que se resuelve.

    11. 2PC frente a 2PLBanco de retos

    Sección titulada «11. 2PC frente a 2PL»

    Define en una frase el propósito de:

    • two-phase commit;
    • two-phase locking.

    Después muestra cómo un sistema simple puede usar ambos en una misma transacción.

    12. Historia de sagaEsencial

    Sección titulada «12. Historia de saga»

    Workflow:

    reservar habitación ✓
cobrar tarjeta       ✓
reservar transporte  ✗

    Diseña compensaciones. Después enumera al menos dos hechos observables que demuestren que compensar no equivale a «nunca ocurrió nada».

    13. Timeout de compensaciónBanco de retos

    Sección titulada «13. Timeout de compensación»

    La operación de reembolso agota su plazo.

    Aplica el razonamiento del Capítulo 4: enumera ejecuciones reales posibles y diseña una estrategia de ID estable para la solicitud de compensación.

    14. Consistent hashingBanco de retos

    Sección titulada «14. Consistent hashing»

    Usa un anillo con posiciones 0..99 y nodos en 10, 40 y 70.

    Con la regla «el primer nodo en sentido horario posee la clave», identifica el propietario de las claves 5, 15, 50 y 90.

    Añade un nodo en 55. ¿Qué claves/rango cambian de propietario?

    15. Remapeo con módulo ingenuoBanco de retos

    Sección titulada «15. Remapeo con módulo ingenuo»

    Para varios hashes de ejemplo calcula hash mod 3 y después hash mod 4.

    Cuenta cuántas claves se mueven. Compara cualitativamente con consistent hashing.

    16. Corte de rebalanceoEsencial

    Sección titulada «16. Corte de rebalanceo»

    El rango R se mueve de A a B.

    Construye un fallo donde:

    copiar snapshot A→B
cliente escribe nuevo valor en A
router cambia a B

    haga desaparecer la escritura.

    Diseña un protocolo de propiedad versionada/cutover que lo evite.

    17. Metadatos de routing obsoletosEsencial

    Sección titulada «17. Metadatos de routing obsoletos»

    El cliente todavía cree que K pertenece a A después de haberse movido a B.

    Compara estas respuestas de A:

    • proxy hacia B;
    • redirección con nuevo epoch;
    • rechazo por propiedad obsoleta;
    • procesar de todas formas.

    ¿Cuál es más segura bajo tu modelo de propiedad y por qué?

    18. Scatter/gatherBanco de retos

    Sección titulada «18. Scatter/gather»

    Una consulta debe contactar cinco shards y responder cuando todos terminen.

    Uno tarda 500 ms y los demás 20 ms.

    ¿Qué ocurre con la latencia total? Propón un contrato de API que permita resultados parciales/degradados y otro que exija completitud.

    19. Arquitectura consciente de particionesBanco de retos

    Sección titulada «19. Arquitectura consciente de particiones»

    Para cada operación decide si intentarías colocar juntos los datos, usar una transacción atómica entre shards o usar saga/workflow eventual:

    • transferencia bancaria;
    • enviar notificación tras actualizar perfil;
    • invitación de calendario de grupo;
    • pipeline de transcodificación;
    • renombrar archivo y actualizar catálogo de metadatos;
    • búsqueda vectorial sobre todas las particiones.

    Defiende cada elección.

    20. Auditoría con IABanco de retos

    Sección titulada «20. Auditoría con IA»

    Pide a un asistente generar código o pseudocódigo de recuperación 2PC. Busca específicamente:

    • voto YES no registrado de forma durable;
    • decisión del coordinador no persistida;
    • participante aborta solo por timeout;
    • COMMIT duplicado aplica dos veces;
    • ID de transacción cambia entre reintentos.

    Para cada problema, indica el invariante violado y un experimento que lo expondría.
