    Aviso sobre referencias de terceros

    Propósito educativo

    Sección titulada «Propósito educativo»

    El curso menciona software, servicios, estándares, proyectos, protocolos, compañías y productos reales porque comparar sistemas ayuda a comprender linaje arquitectónico y compromisos de diseño.

    Referencias como Apache Kafka, Kubernetes, Ray, Amazon S3, WhatsApp, Spotify, Google Calendar, Cloudflare, GitHub Actions, Apache ZooKeeper, etcd u otros sistemas son referencias descriptivas y educativas. No son instrucciones para copiar su identidad visual ni afirmaciones de que el trabajo del estudiante sea una implementación oficial o compatible.

    Titularidad

    Sección titulada «Titularidad»

    Los nombres, marcas, marcas registradas, service marks, logos, trade dress, documentación y otros identificadores protegidos pertenecen a sus respectivos titulares.

    Aparecen aquí con fines de identificación, historia, comparación arquitectónica, estudio de interoperabilidad cuando se indique y educación.

    El curso, sus tareas y las implementaciones de estudiantes son trabajos independientes y no afirman patrocinio, endorsement, afiliación, certificación, partnership ni compatibilidad oficial.

    Nombres de proyectos

    Sección titulada «Nombres de proyectos»

    Usa nombres genéricos u originales independientes.

    Prefiere:

    Replicated Event Log
Distributed Media Streaming Service
Decentralized Secure Messaging
Cluster Job Orchestrator
Distributed Object Store

    en lugar de nombrar la implementación como una nueva edición, derivado oficial o sustituto de un producto citado.

    Es apropiado escribir:

    «Apache Kafka se usa como comparación para logs replicados particionados y consumer groups».

    No lo es afirmar sin autorización/justificación:

    «Este es el Kafka de la Universidad».

    o:

    «Implementación oficial compatible con Kafka».

    Logos e identidad visual

    Sección titulada «Logos e identidad visual»

    No reutilices logos, iconos, identidad distintiva, screenshots como plantilla de interfaz ni branding de forma que el proyecto parezca oficial.

    Los diagramas deben usar normalmente cajas, nodos, colas, discos, clientes, workers, réplicas y etiquetas de protocolos neutrales.

    Un logo de terceros solo debería aparecer en material docente cuando sea apropiado para identificar/discutir ese sistema; no debe convertirse en identidad visual de la tarea.

    Comparación funcional

    Sección titulada «Comparación funcional»

    Se anima a comparar el sistema educativo con software real.

    Una buena comparación pregunta:

    • ¿qué problema resuelve el sistema real?
    • ¿qué subconjunto aparece en esta tarea?
    • ¿qué garantías ofrece?
    • ¿qué garantías omite deliberadamente tu versión?
    • ¿qué mecanismo arquitectónico es similar?
    • ¿qué mecanismo es diferente?
    • ¿qué requisito de escala/operación explica la diferencia?

    Esto forma parte del aprendizaje y no exige copiar interfaces, código, branding o texto de documentación.

    Estándares y protocolos

    Sección titulada «Estándares y protocolos»

    Cuando un proyecto implemente un protocolo público, cita directamente su especificación.

    Por ejemplo:

    contrato externo: FTP / RFC relevante
arquitectura distribuida interna: diseñada por ti

    Limita cualquier afirmación de compatibilidad al subconjunto efectivamente implementado y probado.

    Software open source

    Sección titulada «Software open source»

    Licencia y marcas son cuestiones separadas.

    Una licencia puede permitir usar/modificar/distribuir código y, al mismo tiempo, el nombre/logo del proyecto seguir sujeto a políticas de marca independientes.

    No asumas que «open source» significa que el nombre del proyecto puede reutilizarse como nombre de tu propio producto o servicio. Licencia de código, política de marcas, atribución y compatibilidad son afirmaciones diferentes y deben revisarse por separado.

    Si incorporas código externo en vez de limitarte a estudiarlo o citarlo, también debes respetar su licencia, notices, atribuciones y cualquier obligación aplicable de redistribución. Este aviso de marcas del curso no sustituye esas obligaciones ni constituye asesoramiento jurídico.

    Cuando solo comparas arquitectura o comportamiento, normalmente es mejor citar la documentación o especificación técnica relevante y explicar con precisión qué idea comparas, en lugar de importar código o identidad visual innecesariamente.

    Texto de disclosure recomendado

    Sección titulada «Texto de disclosure recomendado»

    Puedes adaptar:

    Aviso de referencia de terceros: [SISTEMA/PRODUCTO] se menciona únicamente con fines descriptivos, históricos, técnicos y educativos. Sus nombres, marcas, logos y elementos de marca pertenecen a sus titulares. Este proyecto de curso/estudiante se desarrolla independientemente y no está afiliado, patrocinado, endorsed, certificado ni constituye una implementación oficial de [TITULAR/PROYECTO].

    Dónde incluirlo

    Sección titulada «Dónde incluirlo»

    Cuando un informe o presentación use de manera sustancial sistemas nombrados, coloca un aviso conciso:

    • en referencias/agradecimientos o sección de comparación;
    • en el README si los sistemas externos aparecen prominentemente;
    • en presentaciones cuando se discuta branding/screenshots;
    • cerca de una afirmación explícita de compatibilidad cuando sea legítima.

    No hace falta repetir un párrafo legal largo tras cada aparición.

    El texto puede adaptarse cuando la titularidad, licencia o naturaleza del proyecto de referencia exija mayor precisión. Si haces una afirmación técnica concreta de compatibilidad, documenta también el subconjunto probado, las pruebas ejecutadas y las diferencias conocidas; el aviso de terceros no convierte por sí solo esa afirmación en correcta.

    Convención del catálogo

    Sección titulada «Convención del catálogo»
    1. la tarea usa un título educativo genérico;
    2. los sistemas históricos/cercanos aparecen en una sección separada;
    3. son objetivos de estudio/comparación, no requisitos de implementación;
    4. la metodología y esta página proporcionan la política común.

    Así se conserva el valor pedagógico de estudiar sistemas reales manteniendo clara la diferencia entre estudiar un sistema y reclamar su identidad.
