    Schedule

    Final project schedule

    Section titled “Final project schedule”
    Part Date Submission or examination
    1. Ray implementation December 1, 2026, 11:59:59 pm UTC−04:00 Submit a working implementation of your solution using Ray.
    2. Architecture report January 1, 2027, 11:59:59 pm UTC−04:00 Submit a report explaining the architecture without Ray and each of its components in depth.
    3. Final examination Dates follow the official exam timetable First week (first attempt): oral defense of the project implemented without Ray. Second week (second attempt, revalorization): oral defense under the same requirements. Third attempt: handwritten examination.

    Level-two fault tolerance. For both oral defenses, the system must maintain client-side functionality and recover when any two components fail simultaneously. This includes two logical processes, two entire nodes, or a process and a separate node. Losing a node takes down every process it hosts.

    Project submission

    Architecture report template

    The calendar may shift, but keep the course order stable. Each chapter assumes the vocabulary and evidence habits developed before it.

    Week Course line Main question Primary practical
    0 Laboratory Bootcamp How do you create reproducible evidence on one machine? Multi-process environment, structured logs, controlled delay/crash
    1 Thinking in Distributed Systems What changes when a call crosses an independent failure boundary? Local-vs-remote partial-failure experiment
    2 Architectures and Middleware What responsibilities are placed where, and what does middleware hide? Architecture comparison, Ray tasks/actors, dependency map
    3 Processes, Virtualization, and Distributed Execution Which boundaries isolate state and failure? Concurrency diagnosis plus process/container comparison
    4 Communication I What does a timeout actually tell you? Explicit RPC, deadlines, request IDs, safe retry
    5 Communication II How should information move when one request/response path is not enough? Async redelivery comparison plus gossip/dissemination or overlay experiment
    6 Coordination I How can you order events when clocks disagree? Cristian/NTP reasoning plus Lamport/vector traces
    7 Coordination II When do exclusion, election, and agreement require different mechanisms? Mutual-exclusion/election warm-up plus quorum/Raft trace and implementation
    8 Naming, Discovery, and Decentralized Lookup How do you find a logical service whose location changes? Registry, leases, stale caches, decentralized lookup comparison
    9 Replication and Consistency Which histories may clients observe? Replicated KV histories plus a small CRDT/convergence experiment
    10 Fault Tolerance I How do you act when failure and slowness look alike? Failure detector, partition campaign, durable restart/replay checkpoint
    11 Fault Tolerance II What if one operation spans several owners? Sharding, 2PC/recovery, ownership movement
    12 Security, Trust, and Operations What changes when a participant may be unauthorized, compromised, overloaded, or hard to diagnose? Tail-latency/backpressure diagnosis, threat model, authenticated boundary, replay test

    Weekly offline-first rhythm

    Section titled “Weekly offline-first rhythm”

    For each chapter:

    1. download or open the chapter package;
    2. read the explanation and work the small traces by hand;
    3. answer the knowledge check before relying on code;
    4. state a prediction for the guided experiment;
    5. run the normal case locally;
    6. inject the assigned failure, timing, concurrency, or workload condition;
    7. collect compact evidence;
    8. compare observation with prediction;
    9. run and extend transparent tests;
    10. write the technical explanation and remaining uncertainty;
    11. reconnect only when you need to synchronize work or use optional external references.

    Cumulative system checkpoints

    Section titled “Cumulative system checkpoints”

    The core practical thread should feel like one system evolving rather than unrelated weekly toys:

    Chapter 1    local vs remote

Chapter 5    dissemination/overlay communication
Chapter 6    causal trace
Chapter 7    coordination/agreement

Chapter 9    replicated state

Chapter 11   multi-owner state

    If the calendar is compressed, shorten optional system-paper discussions and advanced Byzantine/decentralized extensions before removing the communication → coordination → naming → replication → fault-tolerance spine.
