Fault and Workload Scenario Library

This page defines reusable experiment names for the course. A module may use only the subset relevant to its mechanism, but the meaning of a scenario should remain stable across labs and final-project Phase 3.

The purpose is normalization: when you say you tested a minority partition or lost-response retry, the failure shape should remain comparable across different applications.

F0 — Baseline

Section titled “F0 — Baseline”

Run the system with no injected fault under a documented workload.

Record enough information to compare later experiments:

node count
configuration
workload
throughput/latency where relevant
successful operations
state summary

Every fault experiment should have a baseline.

F1 — Single process crash

Section titled “F1 — Single process crash”

Abruptly terminate one non-client service process.

Questions:

  • Which functionality remains available?
  • Which state is lost?
  • How is the failure detected?
  • Is work retried or reassigned?
  • How long until the service reaches a stable post-failure state?

Do not substitute graceful shutdown when the requirement is crash tolerance.

F2 — Crash and restart

Section titled “F2 — Crash and restart”

Kill one process and restart it using its preserved durable state.

Questions:

  • Which state is replayed?
  • Does identity/incarnation change?
  • When is the node ready to serve again?
  • How does it catch up with peers?

F3 — Slow node

Section titled “F3 — Slow node”

Introduce substantial processing or network delay to one node while leaving it alive.

Typical delay:

250–1000 ms

Questions:

  • Is the node suspected as failed?
  • Does it remain on the critical path?
  • Do queues form?
  • Do retries amplify load?

F4 — Packet loss

Section titled “F4 — Packet loss”

Inject bounded packet loss on one communication path.

Typical local-lab range:

5–20%

Interpretation depends on transport. With TCP, loss may primarily appear as retransmission and latency rather than missing application messages.

F5 — Minority partition

Section titled “F5 — Minority partition”

For a five-node consensus-style cluster, split:

2 | 3

For a three-node cluster, isolate one node:

1 | 2

Questions:

  • Which side can make authoritative progress?
  • Does the minority still respond?
  • What happens when the partition heals?

F6 — Symmetric application partition

Section titled “F6 — Symmetric application partition”

Prevent two selected groups from communicating in either direction while clients can still reach one or both sides as defined by the experiment.

Use this for replication, discovery, DHT/gossip, CRDT, and transaction exercises.

F7 — Heal and reconcile

Section titled “F7 — Heal and reconcile”

Remove a previously injected partition or delay.

Measure recovery, not only connectivity:

  • membership convergence;
  • log repair;
  • state convergence;
  • transaction resolution;
  • task rescheduling;
  • readiness.

F8 — Lost response after successful effect

Section titled “F8 — Lost response after successful effect”

Allow a side-effecting operation to execute successfully, but prevent the client from receiving the successful response.

Then retry using the same logical request ID.

This scenario is central to RPC, state-machine, transaction, and agent/tool correctness.

Expected questions:

  • Was the first effect durable?
  • Does the retry duplicate it?
  • Where is the prior result remembered?

F9 — Duplicate request delivery

Section titled “F9 — Duplicate request delivery”

Deliver the same logical request more than once.

Use stable identity so the implementation cannot avoid the problem by claiming each attempt is a new operation.

This tests idempotency/deduplication directly.

F10 — Stale discovery

Section titled “F10 — Stale discovery”

Make a service endpoint disappear while clients or registries still advertise it.

Measure:

failure time
registry expiry/update time
client refresh time
successful reroute time

F11 — Stale replica read

Section titled “F11 — Stale replica read”

Write through one replica/leader and read from a replica intentionally prevented from receiving the update for some interval.

Record the client-visible history and classify it under the claimed consistency model.

F12 — Concurrent conflicting writes

Section titled “F12 — Concurrent conflicting writes”

Start from common state, separate two writers/replicas, apply conflicting updates, then reconcile.

Useful for:

  • version vectors;
  • eventual consistency;
  • CRDTs;
  • last-writer-wins comparison;
  • application conflict handling.

F13 — Coordinator failure during 2PC

Section titled “F13 — Coordinator failure during 2PC”

Crash the coordinator in at least two windows:

before participants prepare

and:

after participants prepare but before they learn the final decision

The second case exposes blocking/recovery semantics.

F14 — Participant failure during 2PC

Section titled “F14 — Participant failure during 2PC”

Crash one participant before and after durable prepare.

Verify whether recovery preserves the participant’s vote/decision obligations.

F15 — Leader failure

Section titled “F15 — Leader failure”

Crash the current leader of a consensus-backed system.

Measure:

  • detection/election time;
  • unavailable interval;
  • new term/leader;
  • fate of uncommitted entries;
  • client retry behavior.

F16 — Overload

Section titled “F16 — Overload”

Offer work faster than sustainable capacity for a bounded interval.

Record:

  • useful throughput;
  • p50/p95/p99 latency;
  • queue depth;
  • rejection rate;
  • timeout rate;
  • retry attempts;
  • recovery time after load returns to normal.

F17 — Retry amplification

Section titled “F17 — Retry amplification”

Run overload or dependency slowdown with naive retry enabled.

Compare:

logical operations
attempts
completed operations

Then introduce backoff, jitter, retry budgets, or admission control and repeat the identical workload.

F18 — Churn

Section titled “F18 — Churn”

For DHT/gossip systems, repeatedly join, leave, or restart members while requests continue.

Measure:

  • lookup success;
  • stale membership duration;
  • routing cost;
  • convergence time;
  • message overhead.

F19 — Disconnected CRDT updates

Section titled “F19 — Disconnected CRDT updates”

Disconnect replicas, apply independent updates, then deliver state/operations in different orders including duplicates.

Verify convergence and separately evaluate application invariants.

F20 — Unauthorized operation

Section titled “F20 — Unauthorized operation”

Authenticate as a valid principal without authority for a selected action.

Verify:

  • the operation is rejected;
  • protected state is unchanged;
  • the event is auditable without leaking secrets.

F21 — Replay of authenticated mutation

Section titled “F21 — Replay of authenticated mutation”

Replay one previously valid authenticated side-effecting request.

Connect security replay handling to the request identity and durable deduplication work from Chapters 4 and 10.

Workload W1 — Sequential sanity

Section titled “Workload W1 — Sequential sanity”

One client performs one operation at a time.

Use this to establish functional correctness before concurrency.

Workload W2 — Concurrent independent keys/jobs

Section titled “Workload W2 — Concurrent independent keys/jobs”

Many clients operate on independent state.

Useful for measuring concurrency without intentional contention.

Workload W3 — Hot key / hot shard

Section titled “Workload W3 — Hot key / hot shard”

Many clients target the same key, leader, worker, or shard.

Use this to expose serialization, contention, and skew.

Workload W4 — Read-heavy

Section titled “Workload W4 — Read-heavy”

Primarily reads with a small fraction of writes.

Useful for replication, caching, and routing experiments.

Workload W5 — Write-heavy

Section titled “Workload W5 — Write-heavy”

Primarily mutations.

Useful for persistence, replication, quorum, and log throughput.

Workload W6 — Cross-shard transfer

Section titled “Workload W6 — Cross-shard transfer”

Operations span at least two shards/participants and require atomicity or compensation.

Compare against an equivalent local-shard operation.

Workload W7 — Fan-out query

Section titled “Workload W7 — Fan-out query”

One logical request waits for several parallel downstream requests.

Useful for tail-latency and partial-result experiments.

Workload W8 — Long-running task

Section titled “Workload W8 — Long-running task”

A job remains active long enough that worker failure, cancellation, progress tracking, or reassignment can occur during execution.

Useful for project topics such as ML training, tournament matches, crawling, and build execution.

Experiment record template

Section titled “Experiment record template”

Every scenario should be recorded as:

scenario: F15 Leader failure
workload: W5 Write-heavy
prediction: ...
configuration: ...
fault trigger: ...
evidence: ...
observed result: ...
conclusion: ...
remaining uncertainty: ...

Final-project use

Section titled “Final-project use”

Phase 3 does not require every scenario. Select the subset that challenges the guarantees claimed by your project, but the common baseline should include categories equivalent to:

single-node failure
restart/recovery
delay or loss
partition + heal
duplicate/lost-response request
concurrent workload
overload

Project-specific scenarios are added on top of this common vocabulary.
