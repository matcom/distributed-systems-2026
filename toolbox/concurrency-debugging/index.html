    Concurrency and Process Debugging

    Use this guide when one distributed node behaves incorrectly even though the network and protocol appear healthy. Many distributed-system bugs are ordinary local concurrency bugs inside one process.

    Separate data races from semantic races

    Section titled “Separate data races from semantic races”

    A data race means unsynchronized concurrent memory accesses where at least one access writes.

    A semantic race is a higher-level ordering bug such as:

    check condition
another goroutine changes state
act using stale assumption

    A program can be data-race free and still have semantic races.

    Use the Go race detector as evidence

    Section titled “Use the Go race detector as evidence”

    Run appropriate workloads with:

    go test -race ./...

    or a race-enabled program execution.

    A positive report is strong evidence of conflicting unsynchronized accesses exercised during that run.

    A clean run does not prove no race exists because unexecuted interleavings remain untested.

    Inventory shared mutable state

    Section titled “Inventory shared mutable state”

    For each process list structures such as:

    • request-deduplication map;
    • membership table;
    • Raft term/log state;
    • queues;
    • connection pools;
    • metrics;
    • shutdown flags.

    Then identify which goroutines read and write each item.

    Protect invariants, not individual lines

    Section titled “Protect invariants, not individual lines”

    This is unsafe if the invariant spans both operations:

    if key not present:
    insert key

    Protect the whole check-and-act transition, or redesign ownership so one goroutine serializes the state transition.

    Inspect deadlock

    Section titled “Inspect deadlock”

    A classic lock cycle is:

    G1 holds A, waits B
G2 holds B, waits A

    Collect goroutine stacks or equivalent waiting evidence. Do not label every stalled service “deadlocked” without proving a wait cycle or permanent wait condition.

    Distinguish starvation

    Section titled “Distinguish starvation”

    If the system as a whole continues progressing while one goroutine repeatedly fails to obtain a needed resource, that is starvation rather than total deadlock.

    Bound concurrency

    Section titled “Bound concurrency”

    One goroutine per request can become one unbounded resource allocation per request.

    Prefer explicit policies for:

    • maximum active handlers;
    • queue capacity;
    • overload rejection;
    • worker pool size;
    • cancellation.

    Observe queueing and memory behavior under sustained load.

    Avoid locks across RPC boundaries

    Section titled “Avoid locks across RPC boundaries”

    Holding a local mutex while making a remote call couples local progress to network and remote-service behavior.

    Before doing so, ask whether the state can be copied/versioned, the remote call can occur first, or the operation can be split into explicit state transitions.

    Local lock versus distributed coordination

    Section titled “Local lock versus distributed coordination”

    A mutex on replica A does not coordinate replica B.

    If correctness requires one authority across nodes, use a distributed protocol/service such as consensus, a lease with well-defined authority, or another mechanism appropriate to the invariant.

    Shutdown evidence

    Section titled “Shutdown evidence”

    Test both:

    • graceful shutdown (SIGTERM/context cancellation);
    • abrupt process death.

    A service that flushes state correctly only during graceful shutdown may still violate crash-recovery requirements.

    Useful evidence

    Section titled “Useful evidence”
    • race-detector output;
    • goroutine stack dump;
    • queue depth;
    • active goroutine count;
    • lock/wait profile;
    • process exit status;
    • structured state-transition logs.

    Recommended use

    Section titled “Recommended use”

    This guide supports Chapter 3 and remains especially useful when debugging the coordination and fault-tolerance implementations in Chapters 7, 10, and 11.
