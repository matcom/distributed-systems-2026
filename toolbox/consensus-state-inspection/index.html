    Consensus and Replicated-State Inspection

    Use this guide when debugging Raft-style election, log replication, state-machine application, snapshots, or recovery. The central rule is: log enough protocol state to reconstruct the invariant without turning logs into the protocol itself.

    Minimum Raft state to observe

    Section titled “Minimum Raft state to observe”

    Useful fields include:

    node_id
role
current_term
voted_for
leader_id
last_log_index
last_log_term
commit_index
last_applied

    For leader-side replication also record, when relevant:

    peer
next_index
match_index

    State transitions matter more than periodic dumps

    Section titled “State transitions matter more than periodic dumps”

    Prefer events such as:

    {"node":"n2","event":"term-change","from":7,"to":8}
{"node":"n2","event":"vote-granted","term":8,"candidate":"n3"}
{"node":"n3","event":"commit-advance","from":14,"to":17}

    rather than printing the complete state every millisecond.

    Election debugging

    Section titled “Election debugging”

    When an election fails, reconstruct:

    1. which node timed out;
    2. which term it entered;
    3. which vote requests were sent;
    4. each receiver’s current term and prior vote;
    5. candidate log freshness;
    6. which votes were granted/rejected;
    7. whether a majority was actually obtained.

    A node becoming candidate is not evidence it became leader.

    Split-vote evidence

    Section titled “Split-vote evidence”

    For a split election, record all votes for one term. Then verify that no node granted two votes in the same term.

    The correct recovery signal is a later term with a successful majority, typically helped by randomized election timeouts.

    Log replication debugging

    Section titled “Log replication debugging”

    For each rejected AppendEntries, capture:

    • leader term;
    • prevLogIndex;
    • prevLogTerm;
    • follower’s corresponding local entry/absence;
    • resulting nextIndex adjustment.

    This is enough to explain prefix mismatch and suffix repair.

    Presence is not commitment

    Section titled “Presence is not commitment”

    Do not treat:

    entry exists on leader

    or even:

    entry exists on one follower

    as commitment.

    Record the quorum evidence and commit-index transition that authorizes state-machine application.

    Commit is not application

    Section titled “Commit is not application”

    Track separately:

    commit_index
last_applied

    A recovering replica may know that entries are committed while still replaying them into application state.

    Readiness may therefore require more than accepting TCP connections.

    Persistent-state crash points

    Section titled “Persistent-state crash points”

    Useful crash-injection windows include:

    term increment → before durable term write
vote grant → before durable vote write
log append → before fsync/persistence boundary
commit known → before application
application → before client response
snapshot write → before metadata update

    The exact persistence model depends on the implementation, but the report should state which ordering is required.

    Client retry inspection

    Section titled “Client retry inspection”

    For one request ID, trace:

    received
proposed
committed
applied
deduplication record stored
response sent/lost
retried to new leader
prior result returned

    This makes the boundary between consensus and application exactly-once effect visible.

    Snapshot inspection

    Section titled “Snapshot inspection”

    A snapshot should be tied to an explicit log boundary, for example:

    last_included_index
last_included_term

    and should contain every piece of application state required for correct replay, including deduplication state if retry semantics depend on it.

    State transfer

    Section titled “State transfer”

    When a follower is too far behind for retained log entries, record:

    • current snapshot boundary;
    • follower’s known progress;
    • snapshot/state-transfer start;
    • install completion;
    • remaining log replay;
    • readiness transition.

    Useful invariant questions

    Section titled “Useful invariant questions”

    Before changing code, ask:

    • Can two nodes both grant a vote in a way that breaks one-vote-per-term?
    • Can a stale-term node influence newer-term authority?
    • Can an entry be applied before commitment?
    • Can committed entries disappear after a leader change?
    • Can duplicate client requests produce duplicate effects?
    • Can restart lose term/vote/log/deduplication state required by correctness?

    Recommended use

    Section titled “Recommended use”

    This guide supports Chapters 7 and 10, and it can also support P18 or any final project if you independently choose a consensus-backed authority model. No final project is required to use that strategy.
